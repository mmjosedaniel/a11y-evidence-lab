# Delivery readiness and open decisions

## Authority and use

This document is part of the authoritative requirements baseline indexed by [Project requirements](../PROJECT_REQUIREMENTS.md). The index defines status vocabulary, priority semantics, ID stability, and precedence. This file describes planned behavior, not implemented behavior; each identified row's recorded status controls.

## Delivery stages

Development has not been authorized. If it is authorized later, the first implementation scope should be one vertical portfolio slice, not six independently generalized subsystems:

1. Freeze the product scope, the three controlled scenario profiles, and their expected deterministic scanner outcomes before implementation. Freeze the exact evaluation inputs, expected retrieved passages, and scoring rubric before inspecting model output; implementation literals that do not affect those outcomes may be chosen during development.
2. Implement one reusable closed loop that accepts one trusted developer/operator-supplied public HTTPS page, runs one complete deterministic scan limited to `image-alt`, `label`, and `color-contrast`, and retains every violation node reported by those rules as an independently addressable Finding with nested minimized evidence. The user then selects one Finding at a time for LangChain-composed retrieval, evidence-sufficiency gating, either deterministic abstention or one eligible structured generation, one human review decision, and later comparison. The user selects one global Local-or-Groq mode for the analysis; Findings never mix providers, batch into one model call, or trigger fallback.
3. Exercise the three canonical happy-path fixture packages once with the capacity-screened local configuration and once with the exact Groq evaluation configuration. Run shared deterministic collection, valid-zero-versus-failed-scan handling, abstention, review, comparison, and the small trusted-input browser checks without duplicating them per provider. Record limitations, but do not derive statistics, provider rankings, support claims, hostile-target safety claims, or generalized quality claims.
4. Keep authenticated targets, crawling, crawler implementation, link discovery, broader rule coverage, downstream batch processing, installers, desktop packaging, signing, updates, uninstall, formal qualification, and release hardening outside the MVP. Also defer production URL-security controls—including DNS/IP filtering, egress mediation, redirect re-attestation, rebinding defenses, adversarial-page qualification, and exhaustive numeric request/resource policies—until demonstrated product need justifies a later decision.

This sequence does not make implementation or release claims. A distributable product would still require the separate security, provider, application-accessibility, packaging, lifecycle, and release gates owned by their requirements modules.

## Principal risks and required mitigations

Each mitigation becomes required before the capability or claim that creates its risk enters an authorized stage; the table is not a demand to build every control in the first portfolio slice. The small portfolio controls in RSK-002, RSK-003, and RSK-006; Groq egress and credential controls in RSK-012; developer-managed local-model setup in RSK-013; and the narrow loopback and content-display controls in RSK-015 and RSK-016 apply to the planned MVP. RSK-007 records an explicitly accepted trusted-input limitation rather than an MVP hardening gate. Authenticated-target support, hostile or private-target containment, production URL-security controls, application-managed artifact lifecycle, concurrent replacement controls, and packaged-release controls remain deferred.

### OD-020 — Authorized public-page analysis scope

**Status:** Accepted for the MVP on 2026-08-25; authorization-attestation, hostile-target containment, and exhaustive numeric-bound clauses partially superseded by OD-021 on 2026-08-27.

OD-020 accepts the smallest public-page interaction that preserves the evidence-first portfolio goal:

- the user supplies one authorized, non-authenticated public HTTPS page, selects one global generation mode, and activates one **Analyze** action;
- one deterministic scan evaluates exactly `image-alt`, `label`, and `color-contrast` and, on success, retains every violation node from those rules as an independent finding;
- native axe `incomplete` or other scanner manual-review observations remain distinct from violations; they can coexist with a completed zero-violation scan but prevent any all-clear interpretation, while a navigation, timeout, or scan failure never looks like a valid zero-finding scan;
- after the complete finding list and its minimized per-finding evidence are available, the user selects one finding at a time for retrieval, evidence-sufficiency gating, structured generation or deterministic abstention, human review, and later comparison;
- one explicit global `Local` or `Groq` mode applies to the analysis. Calls contain one selected eligible finding only; modes never mix within the analysis, findings never batch into one proposal, and no failure causes fallback;
- the three project-owned synthetic profiles and their failing/corrected states remain the canonical, reproducible evaluation inputs and do not enter the user-submitted runtime URL path; and
- a navigation error, finite-timeout expiry, or scan failure stops the run without publishing a completed zero-finding or silently partial result.

[OD-021](#od-021--trusted-operator-url-boundary-for-the-portfolio-mvp) and [ADR-0018](../architecture/decisions/ADR-0018-trusted-operator-url-boundary.md) replace OD-020's earlier authorization-attestation control, hostile-target containment, and exhaustive numeric-bound planning gates. Authorization and selection of an appropriate public target remain the operator's responsibility rather than a condition the application technically proves. Formal security qualification, hostile or private-target support, production URL-security controls, authenticated-page analysis, broader rule coverage, and unrestricted browser automation remain Deferred. Superseded [ADR-0017](../architecture/decisions/ADR-0017-authorized-public-page-scan-boundary.md) preserves the earlier design as decision history.

OD-020 partially supersedes only OD-018's singleton scenario/work-unit wording and OD-019's synthetic-only and one-profile-at-a-time runtime boundary. OD-018's terminal-status, no-overwrite, no-partial-publication, and no queue/concurrency/cancellation/workflow-engine decisions remain Accepted. OD-022 clarifies that starting again creates an independent run without retry lineage. OD-019's exact three rule/WCAG mappings, controlled evaluation profiles, contrast evidence and ordered comparison measure, no authentication, no broader rule coverage, and no crawling/crawler decisions also remain Accepted.

OD-006's minimization, local-retention, and deletion boundary now applies to target-derived public-page records as well as controlled evaluation runs. OD-008's fixture identity remains the deterministic evaluation correlation baseline; OD-022 accepts only exact unique rule-and-locator matching for public-page comparison and classifies missing, changed, duplicate, or ambiguous matches as `inconclusive`. OD-014 continues to exclude unrestricted browser automation; OD-021 permits only the operator-trusted page input and exact three-rule workflow recorded here.

OD-020 clarifies OD-013's “generation run” granularity as the global mode of one PageAnalysisRun. Every selected-finding invocation inherits that immutable choice. After OD-022, a provider failure remains visible and the MVP performs no automatic retry or regeneration. A later explicit attempt or selection of the other provider starts a new independent PageAnalysisRun, without retry linkage, and never mutates or mixes providers inside the earlier run. This clarification does not supersede OD-013's two-provider, exact-Groq-model, shared-contract, or no-fallback decisions.

OD-019's 2026-08-24 wording is preserved unchanged in its register row as decision history. Its final sentence described the detail statuses at that time; OD-004 subsequently accepted the exact closed eight-artifact corpus composition on 2026-08-25. Exact fixture literals and physical layout, detailed evidence allowlists, manual-check wording, and comparison algorithms retain the statuses recorded by their current owning requirements and assessments.

### OD-021 — Trusted operator URL boundary for the portfolio MVP

**Status:** Accepted for the MVP on 2026-08-27.

OD-021 applies YAGNI to the URL-input boundary while preserving OD-020's evidence-first workflow:

- the developer/operator enters one public HTTPS URL, treats it as trusted, and remains responsible for authorization and target suitability;
- the future interface shows that trusted, authorized pages are the only supported use without adding a separate attestation or confirmation workflow;
- the application validates only the small input and workflow conditions needed for this portfolio use case; it does not technically prove that the destination remains public and it makes no malicious-URL, SSRF-safe, private-network-safe, or adversarial-page claim;
- ordinary Playwright navigation runs in a fresh non-persistent context with no imported user profile, cookies, credentials, or authentication state;
- the scan performs no link discovery, crawling, clicks, form submission, uploads, download workflow, or other scripted page interaction;
- one implementation-stage finite navigation timeout prevents indefinite waiting, and the browser context is closed after success or failure;
- the exact three-rule scan either publishes its complete reported collection or exposes navigation, timeout, or scan failure without presenting a completed zero or partial result; and
- DNS/IP classification, application-owned egress mediation, redirect re-attestation, rebinding defenses, per-subresource policy enforcement, an exhaustive numeric limit manifest, and hostile-page qualification are Deferred production-hardening candidates rather than development-authorization gates.

OD-021 partially supersedes only OD-020's authorization-attestation, hostile-target containment, and exhaustive numeric-bound clauses. It does not change one-page cardinality, the exact three rules, all-reported-findings collection, native `incomplete` separation, one selected-finding workflow, global Local-or-Groq selection, provider provenance, no fallback, canonical fixtures, evidence minimization, review, or comparison semantics. [ADR-0018](../architecture/decisions/ADR-0018-trusted-operator-url-boundary.md) records the corresponding architecture decision; [ADR-0017](../architecture/decisions/ADR-0017-authorized-public-page-scan-boundary.md) remains available only as superseded history.

### OD-022 — Portfolio MVP YAGNI simplification

**Status:** Accepted for the MVP on 2026-08-27.

OD-022 removes platform machinery that does not help demonstrate the first end-to-end portfolio slice:

- replace the Chroma service with LangChain's in-process `MemoryVectorStore`, EmbeddingGemma vectors, exact cosine similarity, a broad rule/success-criterion filter, and `k = 3`; Chroma is deferred until a persistent or larger corpus creates a measured need;
- require the developer to install Ollama and pull `embeddinggemma` before retrieval in either mode, and to pull `qwen3.5:4b` before Local generation; the application checks availability only when embedding or Local generation is actually requested and does not own download progress or a model-manager lifecycle;
- persist one versioned `run.json` aggregate in each run directory, nesting findings and their current downstream results; only run, finding, and corpus-passage identities are mandatory, and the MVP generates no Markdown report;
- preserve the original generated proposal and exactly one current human decision—approve, edit and accept, or reject—with its timestamp, optional note, edited proposal when applicable, and required manual judgments; do not build actor identity, per-edit history, superseding proposal versions, or an audit workflow;
- disclose Local or Groq once when the immutable run mode is selected, keep the provider/model visibly labeled, and require an explicit Generate action for every eligible finding; use the actual provider call and returned-output validation instead of a separate connection-check or synthetic-probe subsystem;
- compare public-page findings only when page and scan profiles align and the same rule has one exact unique locator match; ambiguous, missing, or changed matches are `inconclusive`, while controlled fixtures remain the deterministic source for the full comparison demonstration;
- verify the application's own accessibility with semantic implementation, automated checks, one keyboard path, and one screen-reader smoke path; participant recruitment and an exhaustive assistive-technology matrix are deferred; and
- keep the Gherkin documents non-executable and compact: one behavioral example per essential workflow concern and only the true non-negotiable hard boundaries. The fixed six generation evaluations remain three scenarios through Local and the same three through Groq, not a provider comparison.

OD-022 does not remove RAG, LangChain, local embeddings, the local/Groq provider interface, evidence sufficiency, deterministic abstention, citations, human review, or rescan comparison. It narrows OD-006, OD-009, OD-012 through OD-016, and OD-018 only where their earlier wording implied a persistent vector service, application-managed model acquisition, independently versioned child records, audit-style review history, repeated provider preflights, generalized live-page correlation, exhaustive application-accessibility evaluation, or duplicated specifications. The new architecture records preserve the superseded decisions explicitly.
