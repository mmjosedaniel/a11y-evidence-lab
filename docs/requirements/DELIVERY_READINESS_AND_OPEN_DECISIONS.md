# Delivery readiness and open decisions

## Authority and use

This document is part of the authoritative requirements baseline indexed by [Project requirements](../PROJECT_REQUIREMENTS.md). The index defines status vocabulary, priority semantics, ID stability, and precedence. This file describes planned behavior, not implemented behavior; each identified row's recorded status controls.

## Delivery stages

Development has not been authorized. If it is authorized later, the first implementation scope should be one vertical portfolio slice, not six independently generalized subsystems:

1. Freeze the three project-owned controlled scenario profiles as the canonical evaluation baseline, including each profile's failing and corrected state, the accepted closed eight-artifact W3C source pack, the compact fixed evaluation manifest, the directly applicable record semantics, and the exact numeric bounds required by ADR-0017 before development authorization. “Six fixture revisions” is a logical evaluation-state count, not a required physical file or project layout.
2. Implement one reusable closed loop that accepts one user-attested public HTTPS page, runs one complete deterministic scan limited to `image-alt`, `label`, and `color-contrast`, and retains every violation node from those rules with its independently addressable minimized evidence. The user then selects one finding at a time for LangChain-composed retrieval, evidence-sufficiency gating, either deterministic abstention or one eligible structured generation, one human review decision, and later comparison. The user selects one global local-or-Groq mode for the analysis; findings never mix providers, batch into one model call, or trigger fallback.
3. Exercise the three canonical happy-path fixture packages once with the capacity-screened local configuration and once with the exact Groq evaluation configuration. Run shared deterministic collection, valid-zero-versus-coverage-incomplete, abstention, review, comparison, and authorized-URL security checks without duplicating them per provider. Record limitations, but do not derive statistics, provider rankings, support claims, or generalized quality claims.
4. Keep authenticated or non-public targets, unrestricted URL/network access, crawling, crawler implementation, link discovery, broader rule coverage, downstream batch processing, installers, desktop packaging, signing, updates, uninstall, formal qualification, and release hardening outside the MVP until demonstrated product need justifies a later decision.

This sequence does not make implementation or release claims. A distributable product would still require the separate security, provider, application-accessibility, packaging, lifecycle, and release gates owned by their requirements modules.

## Assumptions

| ID | Assumption |
| --- | --- |
| ASM-001 | The user can attest that one submitted public HTTPS page is authorized for analysis and does not require authentication. The accepted URL and browser-network boundary can fail closed before or during a scan. |
| ASM-002 | A frontend developer is available to make the remediation decision. A QA practitioner may reproduce the finding, inspect its evidence, and verify a change as a secondary user. Neither user is treated as a certified accessibility reviewer. |
| ASM-003 | The initial source set can be lawfully captured, versioned, and cited. |
| ASM-004 | The narrow controlled-fixture set and guidance-corpus snapshot are sufficient as the reproducible evaluation baseline for the bounded public-page workflow; live pages are not evaluation-gold inputs. |
| ASM-005 | The reference computer can run the complete local workflow without out-of-memory failure or making the interface unusable; this remains unproven until the practical capacity check is run. |
| ASM-006 | English is sufficient for the first interface, corpus workflow, evaluation set, and generated output. |
| ASM-007 | A user choosing local setup can obtain an approved model artifact, while a user choosing external-API mode can supply an account and credential governed by that provider's terms. Neither is required to use deterministic scanning and stored evidence. |

## Principal risks and required mitigations

Each mitigation becomes required before the capability or claim that creates its risk enters an authorized stage; the table is not a demand to build every control in the first portfolio slice. The bounded public-page controls in RSK-002, RSK-003, RSK-006, and RSK-007; Groq egress and credential controls in RSK-012; explicit local-model acquisition controls in the MVP part of RSK-013; and loopback-service controls in RSK-015 and RSK-016 apply to the planned MVP. Authenticated/private-target support, complex artifact-lifecycle controls in the future part of RSK-013 and RSK-020, concurrent replacement controls in the advanced part of RSK-018, and packaged-release controls in RSK-021 remain deferred. The first slice applies only the narrow form of each risk introduced by its selected modes.

| RSK-004 | A local or Groq-hosted model produces plausible but unsupported or unsafe remediation. | Structured validation, exact citations, abstention, human review, and fixed evaluations. |

| RSK-012 | External-API use leaks sensitive evidence or credentials, incurs unexpected cost, or produces duplicate billable requests. | Protected secrets, per-invocation preflight disclosure, inspectable egress, approved destinations, usage records, no automatic resubmission or fallback, and explicit retry as a new same-mode PageAnalysisRun after failure or ambiguity. |

| RSK-014 | An independently installed local runtime performs automatic update or telemetry networking during a local-mode run. | Record the evaluated runtime behavior and verify that the controlled local-mode workflow has no unexpected non-loopback egress; runtime ownership remains an implementation choice. |

| RSK-016 | Untrusted target, scanner, corpus, or generated content reaches the React DOM or a privileged application boundary and executes markup, script, navigation, or process access. | Unprivileged renderer, text-by-default rendering, separately approved sandboxing for any preview, local assets, content-security policy, runtime schemas, and a narrow authenticated application API. |
| RSK-017 | Record definitions, runtime checks, persisted values, or provider contracts drift apart. | Use one application-owned definition for each first-slice record and validate actual external boundaries. Generated types, standalone validators, compatibility frameworks, and CI drift machinery require a later demonstrated multi-producer or versioning need under OD-015. |
| RSK-018 | A failed or bounded-out scan is presented as a complete zero/partial finding list, or one selected finding's failed downstream attempt corrupts sibling state. | Publish a finding collection only after the exact three-rule scan completes within its accepted boundary; distinguish valid zero from coverage-incomplete/failed while retaining native axe `incomplete` observations separately; process one selected finding at a time; preserve completed scan evidence and sibling states; and expose no queue, parallel fan-out, or interactive cancellation. |
| RSK-019 | A bounded portfolio result is mistaken for provider qualification, broad model support, or a release claim. | Label the fixed manifest non-promotable, bind observations to the exact tested configuration, state limitations, and defer formal support matrices, promotion, and release qualification. |
| RSK-020 | Future managed updates, model removal, repair, or uninstall could cross a storage boundary. | Do not build those capabilities in the MVP; define their containment only if managed artifact lifecycle or distribution is later accepted. |
| RSK-021 | A future packaged or signed artifact could differ from what was evaluated. | Do not make a release claim in the MVP; define packaged-artifact verification only if distribution is later accepted. |
| RSK-022 | Multiple overlapping planning or evaluation authorities make the current decision impossible to reconstruct. | Keep one requirements baseline and one decision register; preserve superseded history without treating candidate assessments as authority. |

### OD-020 — Authorized public-page analysis scope

**Status:** Accepted for the MVP on 2026-08-25.

OD-020 accepts the smallest public-page interaction that preserves the evidence-first portfolio goal:

- the user submits and explicitly attests authorization for one non-authenticated public HTTPS page, selects one global generation mode, and activates one **Analyze** action;
- one deterministic scan evaluates exactly `image-alt`, `label`, and `color-contrast` and, on success, retains every violation node from those rules as an independent finding;
- native axe `incomplete` or other scanner manual-review observations remain distinct from violations; they can coexist with a completed zero-violation scan but prevent any all-clear interpretation, while a coverage-incomplete scan never looks like a valid zero-finding scan;
- after the complete finding list and its minimized per-finding evidence are available, the user selects one finding at a time for retrieval, evidence-sufficiency gating, structured generation or deterministic abstention, human review, and later comparison;
- one explicit global `Local` or `Groq` mode applies to the analysis. Calls contain one selected eligible finding only; modes never mix within the analysis, findings never batch into one proposal, and no failure causes fallback;
- the three project-owned synthetic profiles and their failing/corrected states remain the canonical, reproducible evaluation inputs and do not enter the user-submitted runtime URL path; and
- the scan rejects or stops without publishing a complete result when the accepted authorization, destination, isolation, or resource boundary cannot establish bounded completeness.

[ADR-0017](../architecture/decisions/ADR-0017-authorized-public-page-scan-boundary.md) accepts the security and data-flow gate for this bounded capability. Exact numeric request, redirect, response, page-load, time, memory, node-count, and other resource limits remain open pre-development planning choices that must be frozen before development authorization and fail closed when exceeded. Formal security qualification, release qualification, support claims, authenticated/private-page analysis, broader rule coverage, and unrestricted browser networking remain Deferred.

OD-020 partially supersedes only OD-018's singleton scenario/work-unit wording and OD-019's synthetic-only and one-profile-at-a-time runtime boundary. OD-018's immutable retry, terminal-status, no-partial-publication, and no queue/concurrency/cancellation/workflow-engine decisions remain Accepted. OD-019's exact three rule/WCAG mappings, controlled evaluation profiles, contrast evidence and ordered comparison measure, no authentication, no broader rule coverage, and no crawling/crawler decisions also remain Accepted.

OD-006's minimization, local-retention, and deletion boundary now applies to target-derived public-page records as well as controlled evaluation runs. OD-008's fixture identity remains the deterministic evaluation correlation baseline; exact public-page target correlation remains Proposed in its owning comparison requirements. OD-014's exclusion of arbitrary-target automation continues to exclude unrestricted browser automation and is not contradicted by ADR-0017's narrowly gated, user-attested public-page scanner.

OD-020 clarifies OD-013's “generation run” granularity as the global mode of one PageAnalysisRun. Every selected-finding invocation inherits that immutable choice. Retrying, regenerating, or selecting the other provider requires a new linked PageAnalysisRun and never mutates or mixes providers inside the earlier run; this clarification does not supersede OD-013's two-provider, exact-Groq-model, shared-contract, or no-fallback decisions.

OD-019's 2026-08-24 wording is preserved unchanged in its register row as decision history. Its final sentence described the detail statuses at that time; OD-004 subsequently accepted the exact closed eight-artifact corpus composition on 2026-08-25. Exact fixture literals and physical layout, detailed evidence allowlists, manual-check wording, and comparison algorithms retain the statuses recorded by their current owning requirements and assessments.

## Remaining deferred or implementation-stage choices

OD-001 and OD-003 through OD-020 now have an explicit MVP disposition above. These dispositions do not authorize development and do not turn evaluation candidates into release dependencies. The following narrower choices remain open until implementation is authorized or the deferred capability enters scope:

- the physical fixture file layout and the exact pinned browser, viewport, and page-state literals;
- the exact numeric URL, redirect, request, response, page-load, time, memory, finding-count, and other bounded-scan limits within ADR-0017's accepted fail-closed boundary;
- the exact query/fragment admission rule, redirect identity rule, and privacy-safe public-page target-correlation fields within ADR-0017's accepted boundary;
- the JavaScript runtime, package manager, build tool, local-service framework, and Chroma evaluation topology;
- the full local model digest and runtime configuration that pass the practical reference-PC capacity check;
- exact run filenames and TypeScript record fields within the accepted filesystem and minimal-validation boundaries; and
- every distribution decision, including installer, desktop wrapper, signing, update, repair, uninstall, support matrix, qualification process, and public release claim.

No development may begin until the repository status and agent instructions explicitly authorize it. After authorization, each implementation slice may begin only when its directly applicable Must requirements and open-decision portions have an accepted or explicitly deferred disposition and its small evaluation set is frozen. Unrelated release-only decisions do not block a portfolio slice.
