# Delivery readiness and open decisions

## Authority and use

This document is part of the authoritative requirements baseline indexed by [Project requirements](../PROJECT_REQUIREMENTS.md). The index defines status vocabulary, priority semantics, ID stability, and precedence. This file describes planned behavior, not implemented behavior; each identified row's recorded status controls.

## Delivery stages

Development has not been authorized. If it is authorized later, the first implementation scope should be one vertical portfolio slice, not six independently generalized subsystems:

1. Freeze the three project-owned controlled scenario profiles as the canonical evaluation baseline, including each profile's failing and corrected state, the accepted closed eight-artifact W3C source pack, the compact fixed evaluation manifest, and the directly applicable record semantics. “Six fixture revisions” is a logical evaluation-state count, not a required physical file or project layout.
2. Implement one reusable closed loop that accepts one trusted developer/operator-supplied public HTTPS page, runs one complete deterministic scan limited to `image-alt`, `label`, and `color-contrast`, and retains every violation node reported by those rules with its independently addressable minimized evidence. The user then selects one finding at a time for LangChain-composed retrieval, evidence-sufficiency gating, either deterministic abstention or one eligible structured generation, one human review decision, and later comparison. The user selects one global local-or-Groq mode for the analysis; findings never mix providers, batch into one model call, or trigger fallback.
3. Exercise the three canonical happy-path fixture packages once with the capacity-screened local configuration and once with the exact Groq evaluation configuration. Run shared deterministic collection, valid-zero-versus-failed-scan handling, abstention, review, comparison, and the small trusted-input browser checks without duplicating them per provider. Record limitations, but do not derive statistics, provider rankings, support claims, hostile-target safety claims, or generalized quality claims.
4. Keep authenticated targets, crawling, crawler implementation, link discovery, broader rule coverage, downstream batch processing, installers, desktop packaging, signing, updates, uninstall, formal qualification, and release hardening outside the MVP. Also defer production URL-security controls—including DNS/IP filtering, egress mediation, redirect re-attestation, rebinding defenses, adversarial-page qualification, and exhaustive numeric request/resource policies—until demonstrated product need justifies a later decision.

This sequence does not make implementation or release claims. A distributable product would still require the separate security, provider, application-accessibility, packaging, lifecycle, and release gates owned by their requirements modules.

## Assumptions

| ID | Assumption |
| --- | --- |
| ASM-001 | The developer/operator supplies one trusted, non-authenticated public HTTPS page, is responsible for authorization and target suitability, and understands that the MVP does not technically prove public reachability or safely contain a malicious target. |
| ASM-002 | A frontend developer is available to make the remediation decision. A QA practitioner may reproduce the finding, inspect its evidence, and verify a change as a secondary user. Neither user is treated as a certified accessibility reviewer. |
| ASM-003 | The initial source set can be lawfully captured, versioned, and cited. |
| ASM-004 | The narrow controlled-fixture set and guidance-corpus snapshot are sufficient as the reproducible evaluation baseline for the trusted-input public-page workflow; live pages are not evaluation-gold inputs. |
| ASM-005 | The reference computer can run the complete local workflow without out-of-memory failure or making the interface unusable; this remains unproven until the practical capacity check is run. |
| ASM-006 | English is sufficient for the first interface, corpus workflow, evaluation set, and generated output. |
| ASM-007 | A user choosing local setup can obtain an approved model artifact, while a user choosing external-API mode can supply an account and credential governed by that provider's terms. Neither is required to use deterministic scanning and stored evidence. |

## Principal risks and required mitigations

Each mitigation becomes required before the capability or claim that creates its risk enters an authorized stage; the table is not a demand to build every control in the first portfolio slice. The small portfolio controls in RSK-002, RSK-003, and RSK-006; Groq egress and credential controls in RSK-012; explicit local-model acquisition controls in the MVP part of RSK-013; and the narrow loopback and content-display controls in RSK-015 and RSK-016 apply to the planned MVP. RSK-007 records an explicitly accepted trusted-input limitation rather than an MVP hardening gate. Authenticated-target support, hostile or private-target containment, production URL-security controls, complex artifact-lifecycle controls in the future part of RSK-013 and RSK-020, concurrent replacement controls in the advanced part of RSK-018, and packaged-release controls in RSK-021 remain deferred. The first slice applies only the narrow form of each risk introduced by its selected modes.

Defer rich previews and their sandboxing. |
| RSK-017 | Record definitions, runtime checks, persisted values, or provider contracts drift apart. | Use one application-owned definition for each first-slice record and validate actual external boundaries. Generated types, standalone validators, compatibility frameworks, and CI drift machinery require a later demonstrated multi-producer or versioning need under OD-015. |
| RSK-018 | A failed or timed-out scan is presented as a completed zero/partial finding list, or one selected finding's failed downstream attempt corrupts sibling state. | Publish a finding collection only after the exact three-rule scan completes; distinguish valid zero from navigation, timeout, or scan failure while retaining native axe `incomplete` observations separately; process one selected finding at a time; preserve completed scan evidence and sibling states; and expose no queue, parallel fan-out, or interactive cancellation. |
| RSK-019 | A bounded portfolio result is mistaken for provider qualification, broad model support, or a release claim. | Label the fixed manifest non-promotable, bind observations to the exact tested configuration, state limitations, and defer formal support matrices, promotion, and release qualification. |
| RSK-020 | Future managed updates, model removal, repair, or uninstall could cross a storage boundary. | Do not build those capabilities in the MVP; define their containment only if managed artifact lifecycle or distribution is later accepted. |
| RSK-021 | A future packaged or signed artifact could differ from what was evaluated. | Do not make a release claim in the MVP; define packaged-artifact verification only if distribution is later accepted. |
| RSK-022 | Multiple overlapping planning or evaluation authorities make the current decision impossible to reconstruct. | Keep one requirements baseline and one decision register; preserve superseded history without treating candidate assessments as authority. |

### OD-020 — Authorized public-page analysis scope

**Status:** Accepted for the MVP on 2026-08-25; authorization-attestation, hostile-target containment, and exhaustive numeric-bound clauses partially superseded by OD-021 on 2026-08-27.

OD-020 accepts the smallest public-page interaction that preserves the evidence-first portfolio goal:

- the user supplies one authorized, non-authenticated public HTTPS page, selects one global generation mode, and activates one **Analyze** action;
- one deterministic scan evaluates exactly `image-alt`, `label`, and `color-contrast` and, on success, retains every violation node from those rules as an independent finding;
- native axe `incomplete` or other scanner manual-review observations remain distinct from violations; they can coexist with a completed zero-violation scan but prevent any all-clear interpretation, while a navigation, timeout, or scan failure never looks like a valid zero-finding scan;
- after the complete finding list and its minimized per-finding evidence are available, the user selects one finding at a time for retrieval, evidence-sufficiency gating, structured generation or deterministic abstention, human review, and later comparison;
- one explicit global `Local` or `Groq` mode applies to the analysis. Calls contain one selected eligible finding only; modes never mix within the analysis, findings never batch into one proposal, and no failure causes fallback;
- the three project-owned synthetic profiles and their failing/corrected states remain the canonical, reproducible evaluation inputs and do not enter the user-submitted runtime URL path; and
- a navigation error, finite-timeout expiry, or scan failure stops the run without publishing a completed zero-finding or silently partial result.

[OD-021](#od-021--trusted-operator-url-boundary-for-the-portfolio-mvp) and [ADR-0018](../architecture/decisions/ADR-0018-trusted-operator-url-boundary.md) replace OD-020's earlier authorization-attestation control, hostile-target containment, and exhaustive numeric-bound planning gates. Authorization and selection of an appropriate public target remain the operator's responsibility rather than a condition the application technically proves. Formal security qualification, hostile or private-target support, production URL-security controls, authenticated-page analysis, broader rule coverage, and unrestricted browser automation remain Deferred. Superseded [ADR-0017](../architecture/decisions/ADR-0017-authorized-public-page-scan-boundary.md) preserves the earlier design as decision history.

OD-020 partially supersedes only OD-018's singleton scenario/work-unit wording and OD-019's synthetic-only and one-profile-at-a-time runtime boundary. OD-018's immutable retry, terminal-status, no-partial-publication, and no queue/concurrency/cancellation/workflow-engine decisions remain Accepted. OD-019's exact three rule/WCAG mappings, controlled evaluation profiles, contrast evidence and ordered comparison measure, no authentication, no broader rule coverage, and no crawling/crawler decisions also remain Accepted.

OD-006's minimization, local-retention, and deletion boundary now applies to target-derived public-page records as well as controlled evaluation runs. OD-008's fixture identity remains the deterministic evaluation correlation baseline; exact public-page target correlation remains Proposed in its owning comparison requirements. OD-014 continues to exclude unrestricted browser automation; OD-021 permits only the operator-trusted page input and exact three-rule workflow recorded here.

OD-020 clarifies OD-013's “generation run” granularity as the global mode of one PageAnalysisRun. Every selected-finding invocation inherits that immutable choice. Retrying, regenerating, or selecting the other provider requires a new linked PageAnalysisRun and never mutates or mixes providers inside the earlier run; this clarification does not supersede OD-013's two-provider, exact-Groq-model, shared-contract, or no-fallback decisions.

OD-019's 2026-08-24 wording is preserved unchanged in its register row as decision history. Its final sentence described the detail statuses at that time; OD-004 subsequently accepted the exact closed eight-artifact corpus composition on 2026-08-25. Exact fixture literals and physical layout, detailed evidence allowlists, manual-check wording, and comparison algorithms retain the statuses recorded by their current owning requirements and assessments.

### OD-021 — Trusted operator URL boundary for the portfolio MVP

**Status:** Accepted for the MVP on 2026-08-27.

OD-021 applies YAGNI to the URL-input boundary while preserving OD-020's evidence-first workflow:

- the developer/operator enters one public HTTPS URL, treats it as trusted, and remains responsible for authorization and target suitability;
- the future interface shows that trusted, authorized pages are the only supported use without adding a separate attestation or confirmation workflow;
- the application validates only the small input and workflow conditions needed for this portfolio use case; it does not technically prove that the destination remains public and it makes no malicious-URL, SSRF-safe, private-network-safe, or adversarial-page claim;
- ordinary Playwright navigation runs in a fresh non-persistent context with no imported user profile, cookies, credentials, or authentication state;
- the scan performs no link discovery, crawling, clicks, form submission, uploads, download workflow, or other scripted page interaction;
- one implementation-stage finite navigation timeout prevents indefinite waiting, and the browser context is closed after success or failure;
- the exact three-rule scan either publishes its complete reported collection or exposes navigation, timeout, or scan failure without presenting a completed zero or partial result; and
- DNS/IP classification, application-owned egress mediation, redirect re-attestation, rebinding defenses, per-subresource policy enforcement, an exhaustive numeric limit manifest, and hostile-page qualification are Deferred production-hardening candidates rather than development-authorization gates.

OD-021 partially supersedes only OD-020's authorization-attestation, hostile-target containment, and exhaustive numeric-bound clauses. It does not change one-page cardinality, the exact three rules, all-reported-findings collection, native `incomplete` separation, one selected-finding workflow, global Local-or-Groq selection, provider provenance, no fallback, canonical fixtures, evidence minimization, review, or comparison semantics. [ADR-0018](../architecture/decisions/ADR-0018-trusted-operator-url-boundary.md) records the corresponding architecture decision; [ADR-0017](../architecture/decisions/ADR-0017-authorized-public-page-scan-boundary.md) remains available only as superseded history.

## Remaining deferred or implementation-stage choices

OD-001 and OD-003 through OD-021 now have an explicit MVP disposition above. These dispositions do not authorize development and do not turn evaluation candidates into release dependencies. The following narrower choices remain open until implementation is authorized or the deferred capability enters scope:

- the physical fixture file layout and the exact pinned browser, viewport, and page-state literals;
- the single finite navigation-timeout value and the privacy-safe public-page target-correlation fields within ADR-0018's accepted trusted-input boundary;
- the JavaScript runtime, package manager, build tool, local-service framework, and Chroma evaluation topology;
- the full local model digest and runtime configuration that pass the practical reference-PC capacity check;
- exact run filenames and TypeScript record fields within the accepted filesystem and minimal-validation boundaries;
- every production URL-security decision, including technical public-reachability enforcement, DNS/IP filtering, egress mediation, redirect re-attestation, rebinding defenses, adversarial-page qualification, and exhaustive request/resource limits; and
- every distribution decision, including installer, desktop wrapper, signing, update, repair, uninstall, support matrix, qualification process, and public release claim.

No development may begin until the repository status and agent instructions explicitly authorize it. After authorization, each implementation slice may begin only when its directly applicable Must requirements and open-decision portions have an accepted or explicitly deferred disposition and its small evaluation set is frozen. Unrelated release-only decisions do not block a portfolio slice.
