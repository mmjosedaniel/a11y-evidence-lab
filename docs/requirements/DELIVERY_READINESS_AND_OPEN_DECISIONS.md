# Delivery readiness and open decisions

## Authority and use

This document is part of the authoritative requirements baseline indexed by [Project requirements](../PROJECT_REQUIREMENTS.md). The index defines status vocabulary, priority semantics, ID stability, and precedence. This file describes planned behavior, not implemented behavior; each identified row's recorded status controls.

## Delivery stages

Development has not been authorized. If it is authorized later, the first implementation scope should be one vertical portfolio slice, not six independently generalized subsystems:

1. Freeze the three project-owned scenario profiles and each profile's failing and corrected state, the accepted closed eight-artifact W3C source pack, the compact fixed evaluation manifest, and the directly applicable record semantics. “Six fixture revisions” is a logical state count, not a required physical file or project layout.
2. Implement one reusable closed loop from deterministic scan through evidence capture and LangChain-composed retrieval to the evidence-sufficiency gate, followed by either deterministic abstention or one eligible structured generation, one human review decision, and one rescan comparison; exercise it separately for `image-alt`, `label`, and `color-contrast` rather than introducing multi-finding orchestration. For each eligible generation run, the user explicitly chooses either the downloaded local model or the Groq API; there is no automatic fallback.
3. Exercise the three happy-path cases once with the capacity-screened local configuration and once with the exact Groq evaluation configuration. Run shared deterministic abstention and comparison checks without duplicating them per provider. Record limitations, but do not derive statistics, provider rankings, support claims, or generalized quality claims.
4. Keep live pages, arbitrary URLs, authenticated targets, crawling, crawler implementation, broader scenario coverage, installers, desktop packaging, signing, updates, uninstall, formal qualification, and release hardening outside the MVP until demonstrated product need justifies a later decision.

This sequence does not make implementation or release claims. A distributable product would still require the separate security, provider, application-accessibility, packaging, lifecycle, and release gates owned by their requirements modules.

## Assumptions

| ID | Assumption |
| --- | --- |
| ASM-001 | The MVP analyzes only its three project-owned synthetic controlled scenarios; it accepts no user-supplied or live target. |
| ASM-002 | A frontend developer is available to make the remediation decision. A QA practitioner may reproduce the finding, inspect its evidence, and verify a change as a secondary user. Neither user is treated as a certified accessibility reviewer. |
| ASM-003 | The initial source set can be lawfully captured, versioned, and cited. |
| ASM-004 | A narrow controlled-fixture set and guidance-corpus snapshot are sufficient to test the product hypothesis before broader page support. |
| ASM-005 | The reference computer can run the complete local workflow without out-of-memory failure or making the interface unusable; this remains unproven until the practical capacity check is run. |
| ASM-006 | English is sufficient for the first interface, corpus workflow, evaluation set, and generated output. |
| ASM-007 | A user choosing local setup can obtain an approved model artifact, while a user choosing external-API mode can supply an account and credential governed by that provider's terms. Neither is required to use deterministic scanning and stored evidence. |

## Principal risks and required mitigations

Each mitigation becomes required before the capability or claim that creates its risk enters an authorized stage; the table is not a demand to build every control in the first portfolio slice. Groq egress and credential controls (RSK-012), explicit local-model acquisition controls (the MVP part of RSK-013), and loopback-service controls (RSK-015 and RSK-016) apply to the planned MVP. Live-target controls (RSK-007), complex artifact-lifecycle controls (the future part of RSK-013 and RSK-020), concurrent replacement controls (the advanced part of RSK-018), and packaged-release controls (RSK-021) remain deferred. The first slice applies only the narrow form of each risk introduced by its selected modes.

| ID | Risk | Required mitigation |
| --- | --- | --- |
| RSK-001 | [Automated checks cover only part of web accessibility](https://playwright.dev/docs/accessibility-testing) and may be mistaken for conformance. | Manual checks, visible coverage limits, prohibited-claim tests, and the non-certification boundary. |
| RSK-002 | Dynamic content makes nominally deterministic scans differ. | Record and control page state, environment, timing, and tool versions; allow not-comparable outcomes. |
| RSK-003 | Finding identity breaks after controlled fixture changes. | Correlate by stable fixture target key, scenario ID, rule ID, fixture revision, and minimized rule evidence; treat a selector as supporting only and allow `inconclusive` or `not comparable`. |
| RSK-004 | A local or Groq-hosted model produces plausible but unsupported or unsafe remediation. | Structured validation, exact citations, abstention, human review, and fixed evaluations. |
| RSK-005 | Corpus updates, chunking, or conflicting guidance cause citation drift. | Immutable snapshots, authority metadata, checksums, exact locators, and conflict handling. |
| RSK-006 | Page content or credentials leak through evidence, prompts, logs, or hosted generation. | Keep the MVP synthetic-only; minimize evidence; retain no raw HTML, screenshots, traces, credentials, values, or private URLs; and send Groq only the minimized synthetic evidence and required guidance after an explicit provider choice. |
| RSK-007 | Live URL scanning exposes the host or internal network. | Defer live targets until browser isolation, URL/network policy, authorization, and threat-model gates pass. |
| RSK-008 | A proposed local model exhausts memory or makes the local interface unusable on the reference PC. | Apply the metadata prefilter and one practical complete-workflow capacity check, replace a failing configuration with a smaller candidate, record observed limitations, and make no performance or support claim. |
| RSK-009 | Users overtrust evidence-sufficiency labels or generated language. | Categorical definitions, layer labels, manual review, limitations in context, and no aggregate accessibility score. |
| RSK-010 | The application itself creates accessibility barriers. | WCAG 2.2 AA design target and combined automated, manual, assistive-technology, and user evaluation. |
| RSK-011 | Provider SDK, API, model alias, or structured-output semantics drift and silently change results. | Application-owned contract, capability snapshots, immutable model/version records, provider conformance tests, and explicit updates. |
| RSK-012 | External-API use leaks sensitive evidence or credentials, incurs unexpected cost, or produces duplicate billable requests. | Protected secrets, preflight disclosure, inspectable egress, approved destinations, usage records, no automatic resubmission or fallback, and explicit retry as a new same-mode run after failure or ambiguity. |
| RSK-013 | An explicit local-model download fails, consumes unexpected storage, or leaves an unusable partial artifact. | Before the user starts it, show the source, license, transfer size, estimated storage, destination, and network use; fail clearly without presenting a partial artifact as ready. |
| RSK-014 | An independently installed local runtime performs automatic update or telemetry networking during a local-mode run. | Record the evaluated runtime behavior and verify that the controlled local-mode workflow has no unexpected non-loopback egress; runtime ownership remains an implementation choice. |
| RSK-015 | Another website or local process reaches the loopback web service and reads or changes project data. | Loopback-only binding, host/origin validation, local session authentication, request-forgery protection, and DNS-rebinding tests. |
| RSK-016 | Untrusted target, scanner, corpus, or generated content reaches the React DOM or a privileged application boundary and executes markup, script, navigation, or process access. | Unprivileged renderer, text-by-default rendering, separately approved sandboxing for any preview, local assets, content-security policy, runtime schemas, and a narrow authenticated application API. |
| RSK-017 | Record definitions, runtime checks, persisted values, or provider contracts drift apart. | Use one application-owned definition for each first-slice record and validate actual external boundaries. Generated types, standalone validators, compatibility frameworks, and CI drift machinery require a later demonstrated multi-producer or versioning need under OD-015. |
| RSK-018 | Failed or timed-out sequential work publishes a partial result, or later concurrent, cancelled, or replaced work publishes a stale result. | The first slice publishes only complete results from its single-current-item flow and exposes no interactive cancellation. Identity-first invalidation, cancellation, late-result tests, and generalized cleanup become required only if later work introduces those states under OD-018. |
| RSK-019 | A bounded portfolio result is mistaken for provider qualification, broad model support, or a release claim. | Label the fixed manifest non-promotable, bind observations to the exact tested configuration, state limitations, and defer formal support matrices, promotion, and release qualification. |
| RSK-020 | Future managed updates, model removal, repair, or uninstall could cross a storage boundary. | Do not build those capabilities in the MVP; define their containment only if managed artifact lifecycle or distribution is later accepted. |
| RSK-021 | A future packaged or signed artifact could differ from what was evaluated. | Do not make a release claim in the MVP; define packaged-artifact verification only if distribution is later accepted. |
| RSK-022 | Multiple overlapping planning or evaluation authorities make the current decision impossible to reconstruct. | Keep one requirements baseline and one decision register; preserve superseded history without treating candidate assessments as authority. |

## Remaining deferred or implementation-stage choices

OD-001 and OD-003 through OD-018 now have an explicit MVP disposition above. These dispositions do not authorize development and do not turn evaluation candidates into release dependencies. The following narrower choices remain open until implementation is authorized or the deferred capability enters scope:

- the physical fixture file layout and the exact pinned browser, viewport, and page-state literals;
- the JavaScript runtime, package manager, build tool, local-service framework, and Chroma evaluation topology;
- the full local model digest and runtime configuration that pass the practical reference-PC capacity check;
- exact run filenames and TypeScript record fields within the accepted filesystem and minimal-validation boundaries; and
- every distribution decision, including installer, desktop wrapper, signing, update, repair, uninstall, support matrix, qualification process, and public release claim.

No development may begin until the repository status and agent instructions explicitly authorize it. After authorization, each implementation slice may begin only when its directly applicable Must requirements and open-decision portions have an accepted or explicitly deferred disposition and its small evaluation set is frozen. Unrelated release-only decisions do not block a portfolio slice.
