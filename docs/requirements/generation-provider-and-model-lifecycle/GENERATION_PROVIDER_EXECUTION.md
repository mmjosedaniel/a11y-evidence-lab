# Generation provider execution requirements

## Authority and use

This document is a focused canonical module within [Generation provider and model lifecycle requirements](README.md) and the authoritative requirements baseline indexed by [Project requirements](../../PROJECT_REQUIREMENTS.md). The index defines status vocabulary, priority semantics, ID stability, and precedence. This file describes planned behavior, not implemented behavior; each identified row's recorded status controls.

## LLM provider selection and generation execution

**Decision status:** The interchangeable generation boundary, local-first recommendation, and prohibition on automatic cross-provider fallback are Accepted in [ADR-0001](../../architecture/decisions/ADR-0001-interchangeable-generation-providers.md). [ADR-0014](../../architecture/decisions/ADR-0014-groq-as-mvp-external-generation-provider.md) accepts two explicit generation modes for the MVP: the selected local runtime and Groq as the first and only external provider. The selected mode is fixed for one run; a local failure never sends data to Groq without a new user choice. This 2026-08-25 decision replaces the earlier staged assumption in this module that API mode would follow the first portfolio slice.

| REQ-LLM-001 | Structured generation must be accessed through an application-owned, provider-neutral boundary. Scan, evidence, retrieval, validation, abstention, review, comparison, and provenance behavior must not depend on a particular model vendor, runtime, SDK, or wire format. | Must | Accepted | Architecture and contract inspection |
| REQ-LLM-002 | The MVP must offer, before each generation run, an explicit choice between the configured local model and Groq. | REQ-LLM-003 | Local mode must be the recommended initial choice and must support the complete three-scenario workflow without hosted inference. | REQ-LLM-004 | The MVP must contain one local adapter and one Groq adapter behind the same application-owned boundary. Groq is the first and only external provider in the MVP; additional providers, provider registries, provider comparison, and multi-provider deployment are Deferred. | Must | Accepted | Adapter-boundary and scope inspection |
| REQ-LLM-005 | Every adapter must accept the same normalized evidence, retrieved passages, prompt and schema versions, parameters, and request metadata, and must return a normalized candidate-proposal result, error, and usage envelope. Every candidate proposal must pass the same schema, citation, grounding, prohibited-claim, and human-review controls. Deterministic evidence-sufficiency abstention remains application-owned and occurs before any adapter invocation. | Must | Accepted | Contract, gating, and adversarial tests |
| REQ-LLM-006 | Before generation, the local service must minimally establish the selected mode, exact model identifier, endpoint class, reachability, authentication readiness when applicable, structured-output capability, and input-size fit. A missing mandatory fact prevents invocation and fails the enclosing workflow operation without discarding already retained minimized evidence; an explicit retry creates a new workflow run. A general compatibility or support-qualification matrix is not required for the MVP. Any retained readiness diagnostic must be content-safe and omit secrets, hostnames, user names, stable device identifiers, personal paths, environment contents, and raw probe output. | Must | Accepted | Readiness, degraded-mode, and diagnostic-content checks |
| REQ-LLM-007 | The product must not silently change a model or provider. Retrying or regenerating with any configuration requires explicit user action and creates a new linked workflow run while preserving the prior run and result. Selecting the other provider is a new explicit choice, never fallback. | Must | Accepted | Failure-injection and audit test |
| REQ-LLM-008 | The product must check context fit before a request and must not silently truncate required evidence, guidance, citations, or system constraints. An input that cannot be represented safely must be blocked before provider invocation and must fail the enclosing workflow operation with a content-safe limiting-capability reason; it is not an evidence-sufficiency abstention. Already retained minimized evidence remains available, and an explicit retry creates a new workflow run. | Must | Accepted | Boundary, overflow, failure, and no-invocation checks |
| REQ-LLM-009 | Changing generation mode must not silently change the scanner, corpus snapshot, embedding, retrieval, evidence, or validation configuration. | Must | Accepted | Configuration-isolation inspection |
| REQ-LLM-010 | Provider connection checks must use synthetic, non-sensitive content and must not transmit target evidence, corpus passages, prompts, or run records. | Must | Accepted | Payload inspection |

The `qwen3.5:9b` configuration and local-model comparison are Deferred. Neither the `qwen3.5:4b` configuration nor the initial runtime is a release-qualified end-user recommendation. MVP evidence may describe only that exact controlled configuration and its observed limitations; passing an evaluation does not promote a model, runtime, adapter, or provider into a release dependency. | Must | Accepted | Capacity-screen, labeling, configuration, and claim inspection |
| REQ-LLM-012 | A formal provider support matrix, promotion vocabulary, release qualification, and public support claim are Deferred pending a later release-support decision. | May | Deferred | Scope review |

| REQ-LLM-014 | Formal compatibility and readiness reports are Deferred pending a later support or release decision. | May | Deferred | Scope review |

The MVP must treat authentication, quota, and rate-limit responses as bounded provider failures and must not describe Groq access as permanent, unlimited, or cost-free. | Must | Accepted | Failure handling and public-claim review |

## Groq source basis

The Groq selection was checked against Groq's primary documentation on 2026-08-25:

- [OpenAI compatibility](https://console.groq.com/docs/openai) documents the compatible API surface; it does not make Groq an OpenAI provider.
- [Structured Outputs](https://console.groq.com/docs/structured-outputs) lists strict schema support for `openai/gpt-oss-20b`.
- The [model page](https://console.groq.com/docs/model/openai/gpt-oss-20b), [model catalog](https://console.groq.com/docs/models), and [deprecation notices](https://console.groq.com/docs/deprecations) are the authority for current availability.
- [Rate limits](https://console.groq.com/docs/rate-limits) are account- and model-dependent service constraints and can change; they are not a portfolio guarantee.
