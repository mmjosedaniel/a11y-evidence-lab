# Generation provider execution requirements

## Authority and use

This document is a focused canonical module within [Generation provider and model lifecycle requirements](README.md) and the authoritative requirements baseline indexed by [Project requirements](../../PROJECT_REQUIREMENTS.md). The index defines status vocabulary, priority semantics, ID stability, and precedence. This file describes planned behavior, not implemented behavior; each identified row's recorded status controls.

## LLM provider selection and generation execution

**Decision status:** The interchangeable generation boundary, local-first recommendation, and prohibition on automatic cross-provider fallback are Accepted in [ADR-0001](../../architecture/decisions/ADR-0001-interchangeable-generation-providers.md). [ADR-0014](../../architecture/decisions/ADR-0014-groq-as-mvp-external-generation-provider.md) accepts two explicit generation modes for the MVP: the selected local runtime and Groq as the first and only external provider. [OD-020](../DELIVERY_READINESS_AND_OPEN_DECISIONS.md#od-020--authorized-public-page-analysis-scope) makes that choice global to one PageAnalysisRun: every eligible selected-finding call uses the same mode, one finding per call, with no provider mixing, batching, or fallback. A local failure never sends data to Groq without a new explicitly selected PageAnalysisRun. This 2026-08-25 decision replaces the earlier staged assumption in this module that API mode would follow the first portfolio slice.

| REQ-LLM-001 | Structured generation must be accessed through an application-owned, provider-neutral boundary. Scan, evidence, retrieval, validation, abstention, review, comparison, and provenance behavior must not depend on a particular model vendor, runtime, SDK, or wire format. | Must | Accepted | Architecture and contract inspection |
| REQ-LLM-002 | When a PageAnalysisRun begins, the user must make one explicit global choice between the configured local model and Groq. The selected mode, provider, and exact model identifier must be visible, immutable across every finding in that run, and recorded once in the run context. Selection creates no ProviderInvocation and must not probe a provider or affect scanning; deterministic scanning, evidence inspection, and reopening prior local records remain available when the selected provider is not ready. | Must | Accepted | Page-analysis and mode-isolation demonstration |
| REQ-LLM-003 | Local mode must be the recommended initial choice and must support the bounded public-page, three-rule workflow one selected finding at a time without hosted inference. Groq mode is a separate explicit global choice, not a fallback. A failed local request must remain local and must never trigger a Groq request unless the user starts a new linked PageAnalysisRun and explicitly selects Groq. | Must | Accepted | Failure-injection and network inspection |
| REQ-LLM-004 | The MVP must contain one local adapter and one Groq adapter behind the same application-owned boundary. Groq is the first and only external provider in the MVP; additional providers, provider registries, provider comparison, and multi-provider deployment are Deferred. | Must | Accepted | Adapter-boundary and scope inspection |
| REQ-LLM-005 | Every adapter invocation must contain exactly one user-selected, proposal-eligible finding and must accept the same normalized evidence, retrieved passages, prompt and schema versions, parameters, and request metadata. It must return one normalized candidate-proposal result, error, and usage envelope. Findings must not be batched into one prompt or combined remediation proposal. Every candidate proposal must pass the same schema, citation, grounding, prohibited-claim, and human-review controls. Deterministic evidence-sufficiency abstention remains application-owned and occurs before any adapter invocation; an abstaining finding records no provider-call provenance, request, response, or usage envelope, while its parent analysis may still record the already selected global mode. | Must | Accepted | Contract, per-finding gating, no-batch, and adversarial checks |
| REQ-LLM-006 | Before generation for a selected finding, the local service must minimally establish the run's global mode, exact model identifier, endpoint class, reachability, authentication readiness when applicable, structured-output capability, and input-size fit. A missing mandatory fact prevents invocation and fails that selected FindingWorkflow without discarding the completed scan, sibling findings, or already retained minimized evidence; any explicit retry follows the accepted new-PageAnalysisRun lifecycle. A general compatibility or support-qualification matrix is not required for the MVP. Any retained readiness diagnostic must be content-safe and omit secrets, hostnames, user names, stable device identifiers, personal paths, environment contents, and raw probe output. | Must | Accepted | Readiness, degraded-mode, isolation, and diagnostic-content checks |
| REQ-LLM-007 | The product must not silently change a model or provider. Retrying or regenerating with the same global mode requires explicit user action and creates a new linked PageAnalysisRun while preserving the prior run and result. Selecting the other provider likewise requires a new PageAnalysisRun and a new explicit global choice; it never mutates an existing run and is never fallback. | Must | Accepted | Failure-injection and audit test |
| REQ-LLM-008 | The product must check context fit before each selected-finding request and must not silently truncate required evidence, guidance, citations, or system constraints. An input that cannot be represented safely must be blocked before provider invocation and must fail that selected FindingWorkflow with a content-safe limiting-capability reason; it is not an evidence-sufficiency abstention. The completed scan, sibling findings, and already retained minimized evidence remain available, and any explicit retry follows the accepted new-PageAnalysisRun lifecycle. | Must | Accepted | Boundary, overflow, isolation, failure, and no-invocation checks |
| REQ-LLM-009 | Changing generation mode must not silently change the scanner, corpus snapshot, embedding, retrieval, evidence, or validation configuration. | Must | Accepted | Configuration-isolation inspection |
| REQ-LLM-010 | Provider connection checks must use synthetic, non-sensitive content and must not transmit target evidence, corpus passages, prompts, or run records. | Must | Accepted | Payload inspection |
| REQ-LLM-011 | The first local capacity-screen configuration must use `qwen3.5:4b` through the initial local runtime selected in ADR-0005. The `qwen3.5:9b` configuration and local-model comparison are Deferred. Neither the `qwen3.5:4b` configuration nor the initial runtime is a release-qualified end-user recommendation. MVP evidence may describe only that exact controlled configuration and its observed limitations; passing an evaluation does not promote a model, runtime, adapter, or provider into a release dependency. | Must | Accepted | Capacity-screen, labeling, configuration, and claim inspection |
| REQ-LLM-012 | A formal provider support matrix, promotion vocabulary, release qualification, and public support claim are Deferred pending a later release-support decision. | May | Deferred | Scope review |
| REQ-LLM-013 | General host-compatibility, saved-profile, artifact-integrity, and eligibility matrices are Deferred pending a need beyond the bounded readiness check in REQ-LLM-006. | May | Deferred | Scope review |
| REQ-LLM-014 | Formal compatibility and readiness reports are Deferred pending a later support or release decision. | May | Deferred | Scope review |
| REQ-LLM-015 | The Groq evaluation configuration must use the exact model identifier `openai/gpt-oss-20b` with Groq strict Structured Outputs. This is a Groq provider configuration even though the model identifier begins with `openai/`. The adapter may express the one application-owned output contract in the request schema required by Groq, but that adapter detail does not establish an application-wide JSON Schema or code-generation framework. The model choice is accepted only for the bounded MVP evaluation and is not a release-qualified dependency or a permanence claim; current availability and deprecation status must be checked before an evaluation run. | Must | Accepted | Structured-output and model-identity check |
| REQ-LLM-016 | Groq quota, free-tier availability, and rate limits are external, changeable service conditions. The MVP must treat authentication, quota, and rate-limit responses as bounded provider failures and must not describe Groq access as permanent, unlimited, or cost-free. | Must | Accepted | Failure handling and public-claim review |
| REQ-LLM-017 | A user-configurable remote generation endpoint is a recommended post-MVP candidate, not an MVP capability or committed roadmap feature. Reconsider it only after a demonstrated need to replace the fixed Groq remote path with one constrained remote profile. Any later proposal must remain behind the local service and application-owned provider contract; preserve explicit global per-analysis selection, selected-finding pre-call evidence gating and abstention, minimized disclosed egress, normalized validation and provenance, visible failures, and no automatic fallback; and require a new threat-model and data-flow decision. The smallest candidate permits one active profile with one approved HTTPS origin, model, authentication method, and protocol subset. Unrestricted URLs, arbitrary headers or protocols, universal compatibility claims, dynamic discovery, provider registries, and multiple active external providers remain outside this recommendation. | May | Deferred | Scope, threat-model, data-flow, and architecture review |
| REQ-LLM-018 | Provider disclosure must be mode-specific. Local mode must remain visibly identified before each local selected-finding invocation and state that its model input stays within the approved local/loopback generation boundary. Immediately before every Groq invocation, the product must present a finding-specific remote disclosure that identifies Groq, the exact model and approved destination, the minimized selected-finding evidence and retrieved-guidance categories sent in that call, the provider-controlled service and retention boundary, credential handling, and bounded failure behavior. A prior Groq call's disclosure, a generic provider label, or the local disclosure cannot cover a later Groq call. A Groq call must not contain the target URL, raw/full HTML, screenshots, DOM snapshots, cookies, credentials, entered values, arbitrary page text, hidden content, sibling findings, or prior review history. Each successful remote invocation must remain attributable to its one selected finding without retaining secrets or raw provider payloads. | Must | Accepted | Per-invocation disclosure, egress, credential, and provenance inspection |

## Groq source basis

The Groq selection was checked against Groq's primary documentation on 2026-08-25:

- [OpenAI compatibility](https://console.groq.com/docs/openai) documents the compatible API surface; it does not make Groq an OpenAI provider.
- [Structured Outputs](https://console.groq.com/docs/structured-outputs) lists strict schema support for `openai/gpt-oss-20b`.
- The [model page](https://console.groq.com/docs/model/openai/gpt-oss-20b), [model catalog](https://console.groq.com/docs/models), and [deprecation notices](https://console.groq.com/docs/deprecations) are the authority for current availability.
- [Rate limits](https://console.groq.com/docs/rate-limits) are account- and model-dependent service constraints and can change; they are not a portfolio guarantee.
