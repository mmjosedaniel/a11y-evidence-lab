# Generation provider execution requirements

## Authority and use

This document is a focused canonical module within [Generation provider and model lifecycle requirements](README.md) and the authoritative requirements baseline indexed by [Project requirements](../../PROJECT_REQUIREMENTS.md). The index defines status vocabulary, priority semantics, ID stability, and precedence. This file describes planned behavior, not implemented behavior; each identified row's recorded status controls.

## LLM provider selection and generation execution

**Decision status:** The interchangeable generation boundary, local-first recommendation, and prohibition on automatic cross-provider fallback are Accepted in [ADR-0001](../../architecture/decisions/ADR-0001-interchangeable-generation-providers.md). [ADR-0014](../../architecture/decisions/ADR-0014-groq-as-mvp-external-generation-provider.md) accepts two explicit generation modes for the MVP: the selected local runtime and Groq as the first and only external provider. [OD-020](../DELIVERY_READINESS_AND_OPEN_DECISIONS.md#od-020--authorized-public-page-analysis-scope), as narrowed by [OD-021](../DELIVERY_READINESS_AND_OPEN_DECISIONS.md#od-021--trusted-operator-url-boundary-for-the-portfolio-mvp), makes that choice global to one PageAnalysisRun: every eligible selected-finding call uses the same mode, one finding per call, with no provider mixing, batching, or fallback. [ADR-0020](../../architecture/decisions/ADR-0020-manual-developer-managed-local-model-setup.md) replaces separate provider probes and repeated per-invocation disclosures with attempt-time prerequisite checks, actual-call validation, one concise run-level disclosure, and a persistent provider/model label. [ADR-0023](../../architecture/decisions/ADR-0023-local-mode-data-boundary.md) defines Local mode as an application-owned data boundary: Local-generation prompts and responses cross only the approved Ollama loopback endpoint, and the embedding adapter uses the locally present embedding model through loopback rather than a hosted embedding or vector service. This does not alter the separately authorized minimized Groq generation payload and does not claim offline operation or zero unrelated system egress. A local failure never sends data to Groq without a new explicitly selected PageAnalysisRun.

| REQ-LLM-017 | A user-configurable remote generation endpoint is a recommended post-MVP candidate, not an MVP capability or committed roadmap feature. Reconsider it only after a demonstrated need to replace the fixed Groq remote path with one constrained remote profile. Any later proposal must remain behind the local service and application-owned provider contract; preserve explicit global per-analysis selection, selected-finding pre-call evidence gating and abstention, minimized disclosed egress, normalized validation and provenance, visible failures, and no automatic fallback; and require a new threat-model and data-flow decision. The smallest candidate permits one active profile with one approved HTTPS origin, model, authentication method, and protocol subset. Unrestricted URLs, arbitrary headers or protocols, universal compatibility claims, dynamic discovery, provider registries, and multiple active external providers remain outside this recommendation. | May | Deferred | Scope, threat-model, data-flow, and architecture review |
| REQ-LLM-018 | Historical requirement: provider disclosure was mode-specific before every selected-finding invocation, and every Groq call required a repeated finding-specific notice identifying the provider, model, destination, transmitted data categories, retention boundary, credential handling, and failure behavior. | Must | Superseded by `REQ-LLM-020` through ADR-0020 | Decision-history inspection |
| REQ-LLM-019 | Provider availability is evaluated only when the user explicitly starts generation for an eligible selected finding. Local mode checks the approved Ollama loopback endpoint and presence of `qwen3.5:4b`; Groq mode checks that the fixed adapter configuration and credential are present. The application performs no earlier connection test, synthetic provider request, generalized capability-discovery exchange, or readiness-report workflow. The one actual provider request and runtime validation of its response determine success or visible failure. Missing setup or a failed/invalid response preserves the completed scan, sibling findings, and minimized evidence and never triggers retry or fallback. The deterministic context-fit protection in `REQ-LLM-008` still runs before the actual request. | Must | Accepted through ADR-0020 | Explicit-attempt, no-probe, output-validation, isolation, and no-fallback checks |
| REQ-LLM-020 | At global mode selection, the interface must show one concise run-level disclosure and then keep the selected provider and exact model visibly labeled throughout the PageAnalysisRun. Local disclosure states that generation prompts and responses use the approved loopback Ollama endpoint and a locally present model and are not sent to hosted inference; it makes no offline or system-wide zero-egress claim. Groq disclosure identifies Groq, `openai/gpt-oss-20b`, remote processing, and the minimized selected-finding evidence and required curated-guidance categories that an explicit generation action may send. A separate repeated disclosure or confirmation gate before each invocation is not required. Every call still requires an explicit finding-level generation action, follows the payload and credential restrictions in the privacy requirements, records non-secret finding-specific provenance only when invoked, and never causes provider mixing or fallback. | Must | Accepted through ADR-0020 and narrowed through ADR-0023 | Run-level disclosure, persistent-label, explicit-action, egress, and provenance inspection |

## Groq source basis

The Groq selection was checked against Groq's primary documentation on 2026-08-25:

- [OpenAI compatibility](https://console.groq.com/docs/openai) documents the compatible API surface; it does not make Groq an OpenAI provider.
- [Structured Outputs](https://console.groq.com/docs/structured-outputs) lists strict schema support for `openai/gpt-oss-20b`.
- The [model page](https://console.groq.com/docs/model/openai/gpt-oss-20b), [model catalog](https://console.groq.com/docs/models), and [deprecation notices](https://console.groq.com/docs/deprecations) are the authority for current availability.
- [Rate limits](https://console.groq.com/docs/rate-limits) are account- and model-dependent service constraints and can change; they are not a portfolio guarantee.
