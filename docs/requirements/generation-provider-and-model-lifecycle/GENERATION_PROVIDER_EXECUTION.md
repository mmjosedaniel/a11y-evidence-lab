# Generation provider execution requirements

## Authority and use

This document is a focused canonical module within [Generation provider and model lifecycle requirements](README.md) and the authoritative requirements baseline indexed by [Project requirements](../../PROJECT_REQUIREMENTS.md). The index defines status vocabulary, priority semantics, ID stability, and precedence. This file describes planned behavior, not implemented behavior; each identified row's recorded status controls.

## LLM provider selection and generation execution

**Decision status:** The interchangeable generation boundary, eventual local/API choice, local-first default, and prohibition on automatic cross-provider fallback are Accepted in [ADR-0001](../../architecture/decisions/ADR-0001-interchangeable-generation-providers.md). The first portfolio slice uses one local adapter behind that boundary. User-selectable dual-mode support, detailed adapter implementations, and the first external API provider belong to a later distributable provider-support stage and remain Proposed.

| ID | Requirement | Priority | Status | Planned verification |
| --- | --- | --- | --- | --- |
| REQ-LLM-001 | Structured generation must be accessed through an application-owned, provider-neutral boundary. Scan, evidence, retrieval, validation, abstention, review, comparison, and provenance behavior must not depend on a particular model vendor, runtime, SDK, or wire format. | Must | Accepted | Architecture and contract inspection |
| REQ-LLM-002 | The first portfolio slice must run generation through the provider-neutral boundary with one configured local provider. A later distributable provider-support stage must let the user select a configured local provider or a configured external-API provider. Whenever generation is available, the selected mode, provider, and model must be visible before generation, immutable within a run, and recorded with that run. | Must | Accepted | Stage-appropriate workflow demonstration |
| REQ-LLM-003 | Local mode must be the recommended initial choice and must support the complete selected first-slice workflow without hosted inference. When external-API mode is introduced later, it must remain an explicit user choice and must never become an automatic fallback. | Must | Accepted | Configuration and network test |
| REQ-LLM-004 | The first portfolio slice must include one conforming local adapter. Both modes may be claimed as supported only after a later stage includes at least one conforming local adapter and one conforming external-API adapter. Additional adapters must be addable without changing domain records or workflow-state semantics. | Must | Accepted | Stage-appropriate provider conformance inspection |
| REQ-LLM-005 | Every adapter must accept the same normalized evidence, retrieved passages, prompt and schema versions, parameters, and request metadata, and must return a normalized result, error, and usage envelope. Every output must pass the same schema, citation, grounding, prohibited-claim, abstention, and human-review controls. | Must | Accepted | Contract and adversarial tests |
| REQ-LLM-006 | Before activation, an adapter must report a capability and readiness snapshot including local or external classification, adapter and runtime version, endpoint class, exact model identifier and revision or digest when available, context and output limits, structured-output mechanism, authentication readiness, and health. A configuration missing a required capability must not run. | Must | Accepted | Capability tests |
| REQ-LLM-007 | The product must not silently change a model or provider. Retrying or regenerating with a different configuration requires explicit user action and creates a linked generation run while preserving the prior run and result. | Must | Accepted | Failure-injection and audit test |
| REQ-LLM-008 | The product must check context fit before a request and must not silently truncate required evidence, guidance, citations, or system constraints. An input that cannot be represented safely must be blocked or produce an abstention identifying the limiting capability. | Must | Proposed | Boundary and overflow tests |
| REQ-LLM-009 | Changing a generation provider must not silently change the scanner, corpus, embedding, retrieval, evidence, audit, or validation configuration; those capabilities remain independently configured and versioned. | Must | Proposed | Configuration isolation test |
| REQ-LLM-010 | Provider connection and capability tests must use synthetic, non-sensitive content and must not transmit target, evidence, corpus, prompt, or project content. | Must | Proposed | Network and payload inspection |
| REQ-LLM-011 | The first local capacity-screen configuration must use `qwen3.5:4b` through the initial local runtime selected in ADR-0005. The `qwen3.5:9b` configuration is only a later capacity-screen option and must not enter the quality comparison unless it first passes REQ-QUAL-009. Neither configuration nor the initial runtime is a release-qualified end-user recommendation until it passes every applicable gate. | Must | Accepted | Capacity-screen, labeling, and configuration inspection |
| REQ-LLM-012 | Every support qualification must bind the exact provider profile, artifact and runtime configuration, applicable hardware profile, workload and evaluation authority, and evidence set, then assign one explicit state from the vocabulary later accepted under OD-017. A provider profile may display the state derived for the current qualification context but must not own one universal state. Evaluation admission, capacity qualification, development use, release support, installer inclusion, and signed public distribution remain separate claims; no passing state automatically promotes a later state. | Must | Proposed | Qualification registry, UI-labeling, and release-claim inspection |
| REQ-LLM-013 | Provider readiness must evaluate host compatibility, runtime availability, exact artifact installation and integrity, adapter health and capabilities, and requested-workload eligibility as separate facts. Partial, contradictory, stale, or unknown mandatory facts must block generation for that profile without blocking deterministic scanning, stored evidence, or history. A saved profile must be revalidated before use. | Must | Proposed | Readiness matrix, stale-profile, and degraded-mode tests |
| REQ-LLM-014 | Compatibility and readiness reports must be versioned, bounded, and privacy-safe. They must distinguish total from currently available RAM, VRAM, and storage and must not include hostnames, user names, device serials, stable adapter identifiers, personal paths, environment variables, or raw probe output. Sensitive internal diagnostics must remain separate from the normalized report. | Must | Proposed | Schema, privacy-canary, and probe-normalization tests |
