# Installation and model lifecycle requirements

## Authority and use

This document is a focused canonical module within [Generation provider and model lifecycle requirements](README.md) and the authoritative requirements baseline indexed by [Project requirements](../../PROJECT_REQUIREMENTS.md). The index defines status vocabulary, priority semantics, ID stability, and precedence. This file describes planned behavior, not implemented behavior; each identified row's recorded status controls.

## Installation, first-run setup, and model lifecycle

**Decision status:** Windows installation, normal shortcut-based launch, exclusion of large model artifacts from the base installer, and consent-based first-run provider setup are Accepted in [ADR-0002](../../architecture/decisions/ADR-0002-windows-installation-and-model-acquisition.md). Packaging technology and third-party runtime ownership remain Proposed.

| ID | Requirement | Priority | Status | Planned verification |
| --- | --- | --- | --- | --- |
| REQ-INST-001 | A Windows MVP release must provide an installer, an installed application launcher, a Start menu entry, and a registered uninstaller. Running source commands is a development path, not the release user experience. | Must | Accepted | Clean-machine installation test |
| REQ-INST-002 | One launcher action must start required application-local services, bind the UI only to an enumerated loopback endpoint, wait for readiness, open the web UI in an application-controlled window or isolated browser context, prevent accidental duplicate instances, report startup failures, and provide a clean stop path. An unrestricted personal browser profile must not be used for strict local-only verification. | Must | Accepted | Launch, isolation, failure, and shutdown tests |
| REQ-INST-003 | The base installer must not contain large generation or embedding model artifacts. Acquiring or importing each model must be a separate, explicit post-install action. | Must | Accepted | Installer-content inspection |
| REQ-INST-004 | First-run setup must offer three understandable paths: the local provider profile qualified by the accepted release evaluation, external LLM API configuration, or defer AI setup. It must not present an evaluation-only bootstrap as validated, and it must not install, download, or transmit anything until the user chooses and consents. | Must | Accepted | First-run labeling, workflow, and network test |
| REQ-INST-005 | Local setup must detect and validate supported runtime identity, version, loopback endpoint, installed model identity and digest, and required capabilities. Process or port presence alone is insufficient. | Must | Proposed | Detection and spoofing tests |
| REQ-INST-006 | If the selected runtime is absent or incompatible, setup must offer an approved installation path or official instructions and must not silently install or update a third-party runtime. Any managed runtime acquisition must disclose its vendor, source, license, pinned version, transfer and estimated storage, privilege needs, update behavior, destination, and network use before consent. | Must | Proposed | Missing-runtime and disclosure test |
| REQ-INST-007 | Before a model download, setup must show its purpose, source, license, exact tag and digest when resolvable, transfer size, estimated installed and temporary storage, selected storage destination, network destination, and compatibility guidance, then require affirmative consent. | Must | Accepted | Disclosure and consent inspection |
| REQ-INST-008 | Model acquisition must preflight path permissions and free space, show progress, support safe cancellation and retry or resume when available, verify integrity before activation, keep partial artifacts unavailable, preserve the last valid configuration, and offer cleanup after failure. | Must | Proposed | Failure-injection and integrity tests |
| REQ-INST-009 | The application must support a documented offline provisioning path for approved, pre-obtained artifacts with manifest, integrity, and license metadata. When no generation provider is ready, scanning, evidence inspection, and history must remain usable while generation is visibly unavailable. | Should | Proposed | Offline installation test |
| REQ-INST-010 | Model management must list each installed model's identifier, digest, size, location, source, license, and status, and support verify, select, update, and remove actions. An update must not silently replace the selected digest, and removal must not delete prior evidence, proposals, reviews, or run provenance. | Must | Proposed | Lifecycle and regression tests |
| REQ-INST-011 | Upgrade and uninstall behavior must distinguish application binaries, project data, application-owned models, credentials, and independently installed runtimes. Project data or externally managed runtime data must not be removed without a separate explicit choice. | Must | Proposed | Upgrade and uninstall tests |
| REQ-INST-012 | The Windows installer should support per-user installation without elevation wherever the accepted dependency design permits. Publicly distributed installers and updates must be authenticated according to the accepted signing and update policy. | Should | Proposed | Installation and signature inspection |
| REQ-INST-013 | Application-owned optional artifacts must be selected through a closed acquisition manifest outside React. The renderer may submit only an approved profile or artifact identifier and an explicit intent; it must not supply download URLs, hashes, executable paths, extraction roots, or arbitrary storage destinations. An external runtime such as Ollama may own its model store, but the application must still record the approved profile and observed artifact identity without creating a competing downloader. | Must | Proposed | Boundary, manifest, and adapter tests |
| REQ-INST-014 | The optional-artifact lifecycle must distinguish **absent**, **confirming**, **acquiring**, **verifying**, **installed**, and **activated**, plus bounded cancelled and failed outcomes. Each action must record whether acquisition used a managed download, approved offline import, or runtime-managed pull, and every mechanism must preserve the same verification, installation, and activation boundary. Verification and installation must not silently activate or select a provider, and a failed update must preserve the last verified and selected configuration. | Must | Proposed | Download, offline-import, runtime-pull, state-transition, and recovery tests |
| REQ-INST-015 | A privileged owner must recheck current hardware eligibility, writable destination, and required free space immediately before any acquisition and again before activation. Application-owned downloads and imports must enforce approved sources and, for network mechanisms, approved origins, a fixed redirect-count cap, and revalidation of every redirect hop; they must also enforce declared and observed byte ceilings, isolated partial staging, incremental integrity checks, cancellation cleanup, traversal and link containment, full-tree verification where applicable, and atomic promotion. Externally managed artifacts must be acquired only through the approved runtime adapter or documented user procedure and must expose sufficient observed identity, integrity, progress, cancellation, and lifecycle evidence for the applicable gates; the profile remains ineligible when a mandatory fact cannot be established. | Must | Proposed | Network, redirect, offline-import, runtime-adapter, exact-boundary, corruption, cancellation, and containment tests |
| REQ-INST-016 | Direct recursive deletion of application-owned artifacts must operate only on manifest-owned exact roots after validating their literal ancestors and complete tree and must reject symlinks and Windows reparse points. Externally managed model or runtime stores must be changed only through an approved runtime API or explicit user instructions, never through direct filesystem deletion by this application. Silent uninstall must preserve user data unless exact destructive options were supplied, and repair or update must not remove retained project or externally managed data. | Must | Proposed | Reparse-point, external-store, sentinel, repair, and uninstall tests |
