# Evaluation and acceptance requirements

## Authority and use

This document is a focused canonical module within [Evaluation and release requirements](README.md) and the authoritative requirements baseline indexed by [Project requirements](../../PROJECT_REQUIREMENTS.md). The index defines status vocabulary, priority semantics, ID stability, and precedence. This file describes planned behavior, not implemented behavior; each identified row's recorded status controls.

The first local-only portfolio slice does not require an API adapter. | REQ-EVAL-012 | Every conclusion must bind the exact provider profile, runtime and adapter versions, full model or artifact digest when available, quantization or format, context and parameters, corpus and schema versions, implementation and authority revisions, dependency locks, hardware profile, and applicable evidence digests. ## Proposed stage-scoped acceptance targets

These stage-scoped values are initial hypotheses, not evidence-backed release thresholds. The first portfolio slice uses the smallest shared dataset that can expose an end-to-end failure across the three controlled scenario profiles. It is non-promotable calibration evidence and cannot qualify a provider, implementation, package, or release. Rows concerning advertised provider profiles, installation, or release evidence apply only when those later stages are authorized; they do not block the portfolio demonstration. OD-009 must approve the exact pilot set and any broader datasets, statistical gates, assistive-technology matrices, or public comparative claims before those claims are made.

| Area | Proposed exit target |
| --- | --- |
| End-to-end coverage | Each of the three selected scenarios completes at least one supported path through fixture authorization, exact-rule scan, evidence capture, retrieval, structured generation, one human decision, and one applicable comparison, with one selected item processed at a time. Additional shared cases exercise deterministic abstention without pretending that an abstention is a proposal. |
| Scan repeatability | Three consecutive runs of each scenario's fixed failing and corrected states under its pinned configuration produce identical normalized expected findings and positive target observations. |
| Evidence completeness | Every evaluated finding contains the required provenance and one sanitized source-evidence item; every corrected state contains the minimal positive same-target observation required by its profile. Contrast records retain the scanner-emitted measured and expected ratios, foreground/background colors, font size, and font weight. |
| Evaluation-set sufficiency | Pending OD-009, one versioned shared set of 9–12 synthetic cases covers the three accepted scenario profiles. Report scenario-level and case-level results; do not generalize percentages from this pilot. |
| Retrieval | The directly supporting passage appears within the recorded top five results for every supported gold case. Report Recall@5 and failure examples; defer additional ranking metrics and numeric promotion gates until the dataset is large enough to interpret them. |
| Citations | 100% of displayed citations resolve to the recorded corpus snapshot and support the associated material claim. |
| Grounding | 100% of displayed material generated claims are supported by page evidence and cited guidance, with zero unsupported high-impact remediation claims. |
| Abstention and manual checks | 100% of deliberately insufficient or conflicting generation cases abstain; 100% of designated image-purpose, label-purpose/clarity, and contrast-classification judgment cases include the required manual check with separate execution, observed-outcome, and proposal-relationship states. Ambiguous comparison cases are evaluated separately as inconclusive outcomes. |
| Remediation usefulness | Every non-abstained pilot proposal receives the one-reviewer rubric result; no proposal may be rated unsafe. The pilot does not support a generalized usefulness percentage. |
| Review integrity | 100% of review transitions preserve the original proposal and actor/time history; no rejected proposal appears accepted. |
| Comparison | The fixed fixture pairs produce the applicable `resolved`, `persistent`, and inverse-pair `regressed` outcomes. `Improved` is unavailable to the binary image and label profiles. Contrast cases distinguish a native failing-to-non-failing `resolved` result from a correlated still-failing result whose later measured-minus-expected contrast margin is strictly higher and therefore `improved`; the latter may be a record-level comparison case and does not require another primary scenario. Missing, changed, or insufficient measurement evidence remains `inconclusive` or pair-level `not comparable`. |
| Prohibited claims | Zero generated, displayed, or exported claims of certification, legal compliance, complete success-criterion conformance or non-conformance, or whole-page/site accessibility. |
| Local-only network behavior | The controlled-fixture evaluation completes with zero non-loopback connections from application-owned services and controlled UI/scan-browser processes, and with only enumerated local-service loopback endpoints. The MVP has no live-target input, link discovery, crawling, or crawler implementation. Any later live-target capability requires a separately authorized scope and evaluation authority. |
| Application accessibility | Core workflows pass the approved WCAG 2.2 AA checklist, automated checks, keyboard review, and every supported screen-reader scenario with no unresolved critical blocker under the approved severity scale. |
| Resource use | Every evaluated local model has already passed the capacity gate, and the core flow completes without out-of-memory failure on the reference machine while meeting latency and resource budgets approved after baseline measurement. |
| Provider conformance | Every advertised local or external-API provider profile passes the shared provider-conformance suite, and forced provider failures cause no undisclosed egress or cross-provider fallback. |
| Work lifecycle integrity | The first sequential, single-current-item flow publishes only complete current results. Replacement queues, interactive cancellation, resume, distributed recovery, and generalized worker orchestration are evaluated only if a later design introduces them. |
| Installation and setup | On a supported clean Windows environment, installation, first launch, each provider-setup path, model-download failure recovery, upgrade, and uninstall satisfy the accepted lifecycle requirements without losing retained project data. |
| Release evidence | Every advertised claim is backed by the exact production inventory and artifact digests for its validation class; missing packaged, exact-host, lifecycle, signing, or provider-profile evidence remains visibly unqualified. |
