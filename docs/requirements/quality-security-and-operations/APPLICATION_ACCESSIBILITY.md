# Application accessibility requirements

## Authority and use

This document is a focused canonical module within [Quality, security, and operations requirements](README.md) and the authoritative requirements baseline indexed by [Project requirements](../../PROJECT_REQUIREMENTS.md). The index defines status vocabulary, priority semantics, ID stability, and precedence. This file describes planned behavior, not implemented behavior; each identified row's recorded status controls.

## Accessibility of A11y Evidence Lab

WCAG 2.2 Level AA is the proposed design and internal verification target for the application's own web interface. This target does not turn the product into a certification service and must not be presented as third-party certification.

[OD-020](../DELIVERY_READINESS_AND_OPEN_DECISIONS.md#od-020--authorized-public-page-analysis-scope), as narrowed by [OD-021](../DELIVERY_READINESS_AND_OPEN_DECISIONS.md#od-021--trusted-operator-url-boundary-for-the-portfolio-mvp), replaces the synthetic single-finding runtime with one trusted operator-supplied public-page scan and a complete variable Finding list. The requirements below therefore apply to URL entry and the documentation-owned trusted-input limitation, scan status, the grouped Findings and ScannerReviewObservations, one selected FindingWorkflow, proposal-only individual review, and comparison. They do not require rendering the scanned page inside the application or repeating that limitation in the ready form or Results through OD-027.

[OD-024](../DELIVERY_READINESS_AND_OPEN_DECISIONS.md#od-024--minimum-complete-mvp-behavior-contracts) accepts the minimum keyboard, semantic, readable, status-announcement, results-navigation, and focus behavior below. `REQ-A11Y-006` remains the complete MVP verification boundary; acceptance does not add a browser or assistive-technology matrix.

| ID | Requirement | Priority | Status | Planned verification |
| --- | --- | --- | --- | --- |
| REQ-A11Y-001 | URL entry, global provider-mode selection, the **Analyze** action, complete-results navigation, one FindingWorkflow selection, evidence/citation inspection, proposal-only individual review, manual checks, and rescan comparison must be operable with a keyboard, with logical focus order, visible focus, and no keyboard trap. The trusted-input limitation remains documented under OD-021 but is not an M1-04 visible control through OD-027. | Must | Accepted through OD-024 and narrowed through OD-027 | One manual keyboard smoke path |
| REQ-A11Y-002 | Page identity, concise supported-check/non-certification limitation, grouped Findings with visibly and programmatically tagged manual-review items, canonical workflow states, review controls, validation, and truthful `running`, `completed`, or `failed` changes must use semantic HTML, accessible names and relationships, and meaningful status announcements. Manual-review observations share the user-facing check groups and selected-evidence workspace while remaining distinct from Findings in canonical data and totals. The trusted-input boundary remains an operational and documentation requirement but is not repeated as visible Analyze/Results copy. No separate progress subsystem or visible lifecycle field is required. | Must | Accepted through OD-024 and narrowed through OD-027, retaining the OD-022 narrowing | Automated check plus one screen-reader smoke path |
| REQ-A11Y-003 | Text, evidence layers, citations, tables, differences, and status indicators must meet applicable contrast, reflow, zoom, and non-color requirements. | Must | Accepted through OD-024 | Automated check and smoke-path review |
| REQ-A11Y-004 | Scan start and completion or failure, valid-zero results, coverage-incomplete scans, FindingWorkflow selection and state changes, errors, abstentions, saved decisions, and comparison results must use one shared announcement pattern without disrupting focus or causing a user to lose their place in the results list. When a later provider-relevant workflow exists, the pattern must also announce whether an actual provider invocation was attempted or failed; deterministic scan-only Results do not announce absent provider activity. This requirement does not create a progress meter or provider-call state machine. | Must | Accepted through OD-024 and narrowed through OD-027, retaining the OD-022 narrowing | Screen-reader smoke path |
| REQ-A11Y-005 | If a later product renders deliberately inaccessible fixture content inside its interface, that content must be isolated and preceded by a clear warning so that it does not make the surrounding application unusable. The portfolio MVP renders neither runtime target pages nor controlled-fixture page content in its interface. | Must | Deferred until an embedded fixture preview is accepted after the portfolio MVP through OD-023 | Later embedded-preview review |
| REQ-A11Y-006 | MVP interface review must use an automated accessibility check plus one documented manual keyboard smoke path and one documented screen-reader smoke path. Each manual path covers trusted public-URL entry, **Analyze**, the complete results list, one selected proposal-bearing FindingWorkflow and its review decision, and one comparison result. `REQ-A11Y-004` separately covers announcing an abstention without creating a review decision. These checks are portfolio evidence only and do not establish a browser, assistive-technology, support, or release matrix. | Must | Accepted through OD-022 and clarified through OD-007 | Automated check and two manual smoke paths |
| REQ-A11Y-007 | Disabled-participant recruitment and formal usability research are outside the portfolio MVP. Reconsider them if the project moves beyond a developer-operated demonstration or intends to make broader usability claims. | May | Deferred | Later product-stage decision |
| REQ-A11Y-008 | Exhaustive browser, assistive-technology, workflow-state, and error-state matrices are outside the portfolio MVP. Reconsider them before the project claims broader browser or assistive-technology support. | May | Deferred | Later support or release decision |
| REQ-A11Y-009 | The complete result view must expose an accessible heading and one overview, user-facing check groups containing every Finding and ScannerReviewObservation, stable human-readable accessible names, concise affected-element summaries, an explicit **Needs manual review** tag for every observation, and a programmatically determinable indication of the selected item. Internal finding IDs, raw lifecycle labels, and native check-group names are not required in the primary interface. The interface must not rely on color, position, item count, or visual grouping alone, and it must not silently omit an item from keyboard or assistive-technology navigation. | Must | Accepted through OD-024 and narrowed through OD-027 | Covered by the two smoke paths |
| REQ-A11Y-010 | Selecting one Finding or ScannerReviewObservation in the grouped list must keep focus on that selected item while updating the shared evidence workspace, and must clearly announce the selected human-readable item without implying that sibling items changed. Provider context and provider-call outcome are included in that announcement only when a later provider-relevant workflow state exists; deterministic scan-only selection does not announce absent provider activity. | Must | Accepted through OD-024 and narrowed through OD-027 | Focus-retention and announcement smoke review |

The two smoke paths are the complete MVP manual accessibility matrix. Recruiting disabled participants, testing additional browser and assistive-technology combinations, exhaustively combining every workflow, busy, disabled, and error state, and rendering inaccessible fixture previews are valuable later product work, but they are not portfolio-development or acceptance gates.
