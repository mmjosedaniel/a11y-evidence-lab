# Reliability, reproducibility, and operations requirements

## Authority and use

This document is a focused canonical module within [Quality, security, and operations requirements](README.md) and the authoritative requirements baseline indexed by [Project requirements](../../PROJECT_REQUIREMENTS.md). The index defines status vocabulary, priority semantics, ID stability, and precedence. This file describes planned behavior, not implemented behavior; each identified row's recorded status controls.

## Decision history

OD-010, OD-011, OD-015, and OD-018 were resolved on 2026-08-25. Rows below that moved from Proposed to Accepted define only the proportional MVP controls. Rows moved from Proposed to Deferred retain their stable IDs for a later, explicitly authorized performance, support, packaging, or release stage.

`REQ-QUAL-010` was already Accepted, but OD-015 narrows its earlier broad interpretation: MVP runtime validation is limited to the URL input, axe result, actual local or Groq provider response, and persisted `run.json` read boundaries. It does not require a universal schema platform, a separate provider probe, or a capability-preflight subsystem. `REQ-QUAL-009` remains the local-model capacity gate, planned for this portfolio scope as one documented manual smoke run on the reference PC rather than application-owned hardware monitoring or support qualification.

[OD-020](../DELIVERY_READINESS_AND_OPEN_DECISIONS.md#od-020--authorized-public-page-analysis-scope) supersedes the synthetic-only and one-rule-per-scan wording retained under stable IDs `REQ-QUAL-003` and `REQ-QUAL-012`. One public-page scan now owns one developer-selected public HTTPS main page and the exact three-rule profile, while controlled fixtures remain the fixed evaluation baseline. All downstream retrieval, generation, abstention, and review work remains sequential for one selected finding at a time. [OD-021](../DELIVERY_READINESS_AND_OPEN_DECISIONS.md#od-021--trusted-operator-url-boundary-for-the-portfolio-mvp) and [ADR-0018](../../architecture/decisions/ADR-0018-trusted-operator-url-boundary.md) replace ADR-0017's hostile-target expansion: `REQ-QUAL-010`, `REQ-QUAL-012`, `REQ-QUAL-013`, and `REQ-QUAL-019` are narrowed below, while the exhaustive bound manifest in `REQ-QUAL-014` and its exact-limit/no-bypass proof in `REQ-QUAL-017` are Deferred. They no longer block development of the trusted-input portfolio slice.

For the portfolio MVP, one `PageAnalysisRun` has one canonical `run.json` aggregate. Findings and the state reached for a user-selected finding are nested in that aggregate; the MVP does not require independently versioned child files, an event store, an audit log, a recovery journal, or a generated Markdown report. The developer installs and starts the local runtime and obtains the selected models manually. The application reports unavailable dependencies and actual provider-call failures but does not supervise the runtime, monitor hardware continuously, or run a separate readiness/probe workflow.

Each public-page runtime scan remains limited to one trusted developer-supplied non-authenticated public HTTPS main page and exactly the three accepted rules; fixed evaluations use only the enumerated project-owned fixtures. Link discovery, following navigation as scan targets, crawling, authentication, imported browser state, arbitrary protocols, multi-page intake, scheduled monitoring, and crawler implementation are not reliability obligations. Hostile or private targets are unsupported rather than production-qualified.

## Deferred exhaustive bounds and enforcement proof

OD-021 removes the production hostile-target bound manifest, connection-gate proof, and below/exact/maximum-plus-one matrix from the portfolio MVP readiness gate. The initial implementation needs one simple configured navigation/scan timeout, cleanup on every terminal path, and the complete-result semantics in `REQ-QUAL-012` and `REQ-QUAL-019`. Exact URL, redirect, request, transfer, DOM, finding-count, evidence-size, memory, process, and temporary-storage ceilings are Deferred until hostile or arbitrary URL support, production distribution, or observed resource failure creates a demonstrated need.

## Accepted manual local-capacity smoke

Before the fixed local-generation evaluation, the developer checks the selected model's published artifact and storage information and performs one representative evidence-sufficient finding workflow on the documented reference PC. The manual note records the machine identity, local runtime and model identity, whether the workflow completed without out-of-memory failure, whether the interface remained usable, and any obvious limitation. No application feature samples GPU, CPU, memory, temperature, or paging, and no repeated benchmark or automated capacity harness is required.

The three fixed local happy-path cases remain functional portfolio evaluations after that one-time smoke; they are not three additional capacity qualifications. The public-page check still exercises URL parsing, the fresh context, complete exact-three-rule scanning, all-finding preservation, and visible failure without turning findings into an automatic generation batch. The three Groq cases validate the shared output contract separately and are not local-capacity evidence. Neither mode is ranked against the other, and no performance, provider, hardware-support, or release claim follows from these observations.

## Public-page reliability source basis

- Playwright documents isolated [browser contexts](https://playwright.dev/docs/browser-contexts) and navigation failure behavior in [`page.goto`](https://playwright.dev/docs/api/class-page#page-goto).
- The version-pinned axe-core [API documentation](https://github.com/dequelabs/axe-core/blob/v4.13.0/doc/API.md) defines `axe.run`, result categories, rule selection, and output used at the scanner boundary.
