# Privacy and security requirements

## Authority and use

This document is a focused canonical module within [Quality, security, and operations requirements](README.md) and the authoritative requirements baseline indexed by [Project requirements](../../PROJECT_REQUIREMENTS.md). The index defines status vocabulary, priority semantics, ID stability, and precedence. This file describes planned behavior, not implemented behavior; each identified row's recorded status controls.

## Privacy and security

**URL-retention clarification (2026-08-30):** The owner reaffirmed the trusted-developer portfolio scope recorded in [ADR-0018](../../architecture/decisions/ADR-0018-trusted-operator-url-boundary.md#trusted-operator-input). In supported use, the developer chooses non-sensitive public URLs suitable for local provenance, including ordinary redirect destinations. Standards-normalized requested and observed final URLs may be retained in run provenance only, with basic HTTPS/credential validation. The MVP does not classify arbitrary URL components, certify their non-sensitivity, add a URL-approval control, or create a partial/withheld page-identity subsystem. This assumption does not authorize credentials, private URLs, sensitive page evidence, or URL disclosure to a provider; the exclusions in `REQ-SEC-002`, `REQ-SEC-003`, and `REQ-SEC-015` remain applicable. Basic validation does not prove semantic non-sensitivity when the supported-use assumption is violated.

**MVP decision status:** [OD-020](../DELIVERY_READINESS_AND_OPEN_DECISIONS.md#od-020--authorized-public-page-analysis-scope) admits one public HTTPS page per PageAnalysisRun. [OD-021](../DELIVERY_READINESS_AND_OPEN_DECISIONS.md#od-021--trusted-operator-url-boundary-for-the-portfolio-mvp) and [ADR-0018](../../architecture/decisions/ADR-0018-trusted-operator-url-boundary.md) retain that interaction but replace ADR-0017's production hostile-target model with a trusted developer-input portfolio boundary. The developer is responsible for choosing a benign page they are permitted to analyze. The application does not independently prove public reachability or protect against hostile URLs, private-address targeting, redirect abuse, DNS rebinding, malicious subresources, or browser-network bypass. [OD-022](../DELIVERY_READINESS_AND_OPEN_DECISIONS.md#od-022--portfolio-mvp-yagni-simplification) and [ADR-0021](../../architecture/decisions/ADR-0021-single-file-run-aggregate.md) narrow persistence to one `run.json` in one deletable run directory, while [ADR-0014](../../architecture/decisions/ADR-0014-groq-as-mvp-external-generation-provider.md) still limits external generation to Groq and prohibits automatic fallback. [ADR-0023](../../architecture/decisions/ADR-0023-local-mode-data-boundary.md) limits the Local-mode privacy promise to two application-owned operations: Local-generation prompts and responses cross only the approved Ollama loopback boundary, and the embedding adapter uses the local model through loopback rather than a hosted embedding or vector service. The separately authorized minimized Groq generation payload remains unchanged. ADR-0023 rejects a broader claim of offline operation or zero unrelated system egress.

OD-021 supersedes the hostile-target requirements `REQ-SEC-001`, `REQ-SEC-009`, `REQ-SEC-011`, `REQ-SEC-018`, `REQ-SEC-019`, `REQ-SEC-022`, `REQ-SEC-024`, and `REQ-SEC-025` with the proportional `REQ-SEC-026` and `REQ-SEC-027` boundaries below. It defers the connection-level gate in `REQ-SEC-023` and the closed renderer-projection hardening in `REQ-SEC-020`. Their stable IDs and wording remain visible as decision history. ADR-0023 prevents the historical zero-egress language in `REQ-SEC-011` from being interpreted as a current application, runtime, browser, operating-system, or machine-wide requirement. OD-021 does not authorize authentication, browser-profile reuse, crawling, arbitrary protocols, cloud persistence, hosted tracing, telemetry, analytics, or automatic provider retry. Evidence minimization, provider disclosure, credential protection, explicit egress, and content-safe portfolio records remain applicable because they directly support the evidence-first RAG workflow.

## Deferred production hardening

The following controls are intentionally outside the trusted-input portfolio MVP and do not block its development: special-purpose IP and domain classification; connection-level egress gating; DNS-rebinding and browser-bypass proof; redirect re-attestation; exhaustive protocol and subresource controls; adversarial hostile-page qualification; and security-oriented request, transfer, DOM, memory, or process ceilings. They require a new product and threat-model decision if the application later claims to accept arbitrary or hostile URLs safely.

## Deferred public-target security source basis

The following primary sources remain relevant to the superseded ADR-0017 design and any later production hardening. They are not MVP implementation obligations under OD-021:

- The [WHATWG URL Standard](https://url.spec.whatwg.org/) defines interoperable URL parsing and serialization and identifies spoofing and untrusted-URL handling concerns.
- The OWASP [Server-Side Request Forgery Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html) describes protocol allowlisting, redirect control, and validation of every resolved A and AAAA address.
- IANA maintains the authoritative [Special-Use Domain Names](https://www.iana.org/assignments/special-use-domain-names), [IPv4 Special-Purpose Address Space](https://www.iana.org/assignments/iana-ipv4-special-registry), and [IPv6 Special-Purpose Address Space](https://www.iana.org/assignments/iana-ipv6-special-registry) registries used by the public-destination policy.
- Playwright documents isolated non-persistent [browser contexts](https://playwright.dev/docs/browser-contexts), context-wide [network routing and service-worker limitations](https://playwright.dev/docs/network), and the separate [`routeWebSocket`](https://playwright.dev/docs/api/class-browsercontext#browser-context-route-web-socket) boundary.
- Chromium documents the purpose and OS-dependent guarantees of its [browser sandbox](https://chromium.googlesource.com/chromium/src/+/main/docs/design/sandbox.md).

## Groq privacy source basis

The Groq boundary was checked on 2026-08-25 against Groq's primary [security-onboarding guidance](https://console.groq.com/docs/production-readiness/security-onboarding) and [Your Data documentation](https://console.groq.com/docs/your-data). Provider documentation describes provider-side handling; the application must still minimize the payload, disclose that an external service receives it, and avoid claims that local deletion controls provider-side records.
