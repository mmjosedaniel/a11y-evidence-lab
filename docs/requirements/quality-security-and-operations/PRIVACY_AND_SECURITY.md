# Privacy and security requirements

## Authority and use

This document is a focused canonical module within [Quality, security, and operations requirements](README.md) and the authoritative requirements baseline indexed by [Project requirements](../../PROJECT_REQUIREMENTS.md). The index defines status vocabulary, priority semantics, ID stability, and precedence. This file describes planned behavior, not implemented behavior; each identified row's recorded status controls.

## Privacy and security

**MVP decision status:** [OD-020](../DELIVERY_READINESS_AND_OPEN_DECISIONS.md#od-020--authorized-public-page-analysis-scope) and [ADR-0017](../../architecture/decisions/ADR-0017-authorized-public-page-scan-boundary.md) replace the synthetic-only runtime boundary by also admitting one user-attested authorized public HTTPS page per page-analysis run; the three project-owned controlled fixtures remain the fixed evaluation baseline. A public target is hostile input even when publicly reachable. One connection-level egress-gate/proxy module inside the existing local service owns public-destination enforcement; the Playwright browser has no direct-network bypass. [ADR-0016](../../architecture/decisions/ADR-0016-filesystem-run-persistence.md) still defines one deletable local run directory as the persistence unit, while [ADR-0014](../../architecture/decisions/ADR-0014-groq-as-mvp-external-generation-provider.md) still limits external generation to Groq and prohibits automatic fallback.

OD-020 explicitly supersedes the synthetic-only or no-live-network portions of `REQ-SEC-003`, `REQ-SEC-005`, `REQ-SEC-007`, `REQ-SEC-009`, `REQ-SEC-011`, and `REQ-SEC-015`; their stable IDs remain below. ADR-0017 resolves the hostile-target boundary in `REQ-SEC-001` as Accepted and is the authority for new `REQ-SEC-022` through `REQ-SEC-025`; unrelated `REQ-SEC-020` remains Proposed. OD-020 does not authorize authentication, browser-profile reuse, crawling, arbitrary protocols or ports, private-network targets, cloud persistence, hosted tracing, telemetry, analytics, or automatic provider retry. Exact quantitative scan limits and the concrete proof that the managed browser cannot bypass the egress gate remain open pre-development values under the reliability requirements.

## Open pre-development security details

The public-page boundary is Accepted, but development is not authorized until the following enforcement details are resolved and recorded without weakening the requirements above:

- the standards-based URL library behavior for query strings, fragments, internationalized names, canonical display, and rejection of credential-like target material;
- the maintained implementation source for the IANA special-use-domain and IPv4/IPv6 special-purpose classifications;
- the exact same-origin or re-attestation redirect rule and its fixed numeric redirect limit;
- the concrete mechanism and verification environment proving that Playwright-managed Chromium cannot bypass the connection-level gate through HTTP, HTTPS, DNS rebinding, WebSocket, WebRTC, WebTransport, QUIC, a service worker, a popup, or a subframe; and
- the exact allowed subresource request methods and types needed for faithful rendering without enabling form submission, arbitrary interaction, or another page target.

These are bounded implementation decisions for one hostile public page, not authorization for a crawler, general browser-security platform, or separate proxy service.

## Public-target security source basis

- The [WHATWG URL Standard](https://url.spec.whatwg.org/) defines interoperable URL parsing and serialization and identifies spoofing and untrusted-URL handling concerns.
- The OWASP [Server-Side Request Forgery Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html) describes protocol allowlisting, redirect control, and validation of every resolved A and AAAA address.
- IANA maintains the authoritative [Special-Use Domain Names](https://www.iana.org/assignments/special-use-domain-names), [IPv4 Special-Purpose Address Space](https://www.iana.org/assignments/iana-ipv4-special-registry), and [IPv6 Special-Purpose Address Space](https://www.iana.org/assignments/iana-ipv6-special-registry) registries used by the public-destination policy.
- Playwright documents isolated non-persistent [browser contexts](https://playwright.dev/docs/browser-contexts), context-wide [network routing and service-worker limitations](https://playwright.dev/docs/network), and the separate [`routeWebSocket`](https://playwright.dev/docs/api/class-browsercontext#browser-context-route-web-socket) boundary.
- Chromium documents the purpose and OS-dependent guarantees of its [browser sandbox](https://chromium.googlesource.com/chromium/src/+/main/docs/design/sandbox.md).

## Groq privacy source basis

The Groq boundary was checked on 2026-08-25 against Groq's primary [security-onboarding guidance](https://console.groq.com/docs/production-readiness/security-onboarding) and [Your Data documentation](https://console.groq.com/docs/your-data). Provider documentation describes provider-side handling; the application must still minimize the payload, disclose that an external service receives it, and avoid claims that local deletion controls provider-side records.
