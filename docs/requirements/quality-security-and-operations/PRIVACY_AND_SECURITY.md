# Privacy and security requirements

## Authority and use

This document is a focused canonical module within [Quality, security, and operations requirements](README.md) and the authoritative requirements baseline indexed by [Project requirements](../../PROJECT_REQUIREMENTS.md). The index defines status vocabulary, priority semantics, ID stability, and precedence. This file describes planned behavior, not implemented behavior; each identified row's recorded status controls.

## Privacy and security

| ID | Requirement | Priority | Status | Planned verification |
| --- | --- | --- | --- | --- |
| REQ-SEC-001 | Target pages and corpus content must be treated as untrusted. Browser execution, network access, file access, redirects, downloads, and resource consumption must be isolated and constrained. | Must | Proposed | Threat model and security test |
| REQ-SEC-002 | Browser credentials, session tokens, authorization headers, secrets, and unrelated personal data must never be stored as finding evidence or included in traces. | Must | Proposed | Secret-leak test |
| REQ-SEC-003 | Evidence, prompts, logs, and traces must be minimized and deterministically redacted before persistence according to a documented data classification and retention policy. Any permitted sensitive retained payload must have approved encryption and access controls. | Must | Proposed | Privacy audit |
| REQ-SEC-004 | A complete local-only product and evaluation path must operate with hosted inference, cloud tracing, analytics, telemetry, and automatic cloud fallback disabled. | Must | Proposed | Network-disabled evaluation |
| REQ-SEC-005 | External-API LLM mode must be a separate, explicit mode transition. Before activation and after a material profile or policy change, it must disclose the provider and model, destination, data categories sent, redaction behavior, available provider retention information, billing responsibility and cost indicators, retry behavior, and failure behavior. Consent must be recorded and revocable, and the mode must never activate automatically. | Must | Accepted | Configuration, consent, and network review |
| REQ-SEC-006 | The product must support policy-authorized cascading deletion of locally persisted targets, scans, evidence, proposals, reviews, traces, derived embeddings/index entries, exports, and eligible backups. | Must | Proposed | Deletion test |
| REQ-SEC-007 | A public demonstration must use synthetic or explicitly approved non-sensitive fixtures and data. | Must | Accepted | Release inspection |
| REQ-SEC-008 | Dependency, model, and corpus artifacts must have recorded source, version or digest, license, and integrity metadata before distribution. | Must | Proposed | Supply-chain inspection |
| REQ-SEC-009 | A threat model and data-flow review must be accepted before live URL scanning or hosted data egress is developed. | Must | Proposed | Decision review |
| REQ-SEC-010 | Immutability and append-only guarantees apply only while records are retained. After deletion, only a minimal non-sensitive tombstone may remain, recording scope, time, policy basis, and broken-lineage status without recoverable deleted content. | Must | Proposed | Integrity and deletion test |
| REQ-SEC-011 | The controlled-fixture workflow and evaluation suite, including every application-owned service and controlled UI or scan-browser process, must complete with non-loopback egress disabled; only enumerated loopback endpoints for local services are permitted. Live-target mode may contact only destinations allowed by a preapproved policy, and every redirect and subresource destination must be revalidated against that policy. Framework analytics, update checks, crash reporting, browser extensions, and unrelated DNS or network calls must remain disabled in those controlled processes. | Must | Proposed | Process-scoped network inspection |
| REQ-SEC-012 | The local-only path must use a provider-neutral local audit and trace store sufficient for reproducibility when LangSmith or another hosted service is unavailable or disabled. | Must | Proposed | Offline demonstration |
| REQ-SEC-013 | External-provider credentials must be stored only in an operating-system-protected secret facility or an equally approved mechanism. They must never be stored in plaintext project files, application databases, logs, traces, evidence, backups, or exports; after entry they must be masked, replaceable, and deletable and must not be returned to browser code. | Must | Proposed | Secret-storage and leak test |
| REQ-SEC-014 | External adapters may contact only the approved HTTPS destinations recorded in their provider profile; approved loopback runtimes are the only HTTP exception. Endpoint and redirect policy must be validated before activation. Arbitrary custom endpoints are outside the MVP unless an accepted threat model defines their controls. | Must | Proposed | Endpoint and redirect test |
| REQ-SEC-015 | Every external generation request must record a non-secret egress manifest containing the provider profile and capability-snapshot IDs, destination, transmitted data categories and privacy-safe payload checksum, redaction-policy version, consent record, time, outcome, and available usage metadata. The user must be able to inspect the protected outbound payload before transmission. | Must | Proposed | Egress-manifest audit |
| REQ-SEC-016 | Authentication, quota, rate-limit, network, provider, and ambiguous billable-response failures must remain distinguishable. Retries must be bounded, preserve lineage, never cross providers, and must not resubmit an ambiguously completed billable request without an approved safe policy or explicit user action. | Must | Proposed | Failure-injection and billing-safety test |
| REQ-SEC-017 | Installer, runtime, and model acquisition may use non-loopback networking only as a distinct user-initiated setup or update action with the destination, purpose, and expected transfer disclosed. No setup consent authorizes egress during the configured local-only controlled-fixture workflow. | Must | Accepted | Setup and local-only network tests |
| REQ-SEC-018 | Application-local HTTP services must bind only to loopback and must reject unapproved host, origin, cross-site, and DNS-rebinding access. State-changing requests and browser sessions must use an approved local authentication and request-forgery defense without exposing bootstrap secrets in URLs or logs. | Must | Proposed | Local-service penetration test |
| REQ-SEC-019 | Browser-delivered UI code must not receive credentials or expose direct filesystem, process-control, provider, model-runtime, vector-store, or browser-automation access. Target content, scanner output, corpus passages, and generated content must be treated as untrusted and rendered as text unless a separately accepted sandboxing and sanitization design applies. UI assets must be local and constrained by the approved content-security policy. | Must | Accepted | Renderer-boundary, XSS, CSP, and secret-leak tests |
| REQ-SEC-020 | Before React rendering, untrusted scanner, target, corpus, provider, and persisted data must be projected into a closed application-owned view model with exhaustive state handling. The renderer must not use untrusted HTML, `srcdoc`, executable URLs, or navigation targets, use untrusted values as DOM identifiers, or spread untrusted objects into element properties; unavailable actions and links must remain inert with an accessible explanation. | Must | Proposed | Projection-schema, XSS, navigation, and exhaustive-state tests |
| REQ-SEC-021 | Operational diagnostics, promoted evaluation summaries, release evidence, and tracked fixtures must use closed allowlisted schemas and synthetic or explicitly approved content. Raw browser sessions, page captures, prompts, provider payloads, model responses, screenshots, and private evaluation journals must remain in approved protected or ignored storage, undergo bounded safe derivation and privacy-canary checks, and be removed according to the accepted retention policy rather than copied into release evidence. | Must | Proposed | Promotion-schema, ignored-root, privacy-canary, and retention audit |
