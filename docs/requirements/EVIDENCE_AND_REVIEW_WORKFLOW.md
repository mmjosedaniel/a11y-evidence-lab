# Evidence and review workflow requirements

## Authority and use

This document is part of the authoritative requirements baseline indexed by [Project requirements](../PROJECT_REQUIREMENTS.md). The index defines status vocabulary, priority semantics, ID stability, and precedence. This file describes planned behavior, not implemented behavior; each identified row's recorded status controls.

## Current workflow boundary and decision history

**Status:** [OD-020](DELIVERY_READINESS_AND_OPEN_DECISIONS.md#od-020--authorized-public-page-analysis-scope) accepts one public HTTPS page, one provider-independent scan with exactly `image-alt`, `label`, and `color-contrast`, a complete variable collection of violation-node Findings, separate native `incomplete` ScannerReviewObservations, one immutable global Local-or-Groq provider/exact-model context, and one selected FindingWorkflow at a time. [OD-021](DELIVERY_READINESS_AND_OPEN_DECISIONS.md#od-021--trusted-operator-url-boundary-for-the-portfolio-mvp) and [ADR-0018](../architecture/decisions/ADR-0018-trusted-operator-url-boundary.md) replace its production hostile-target controls with a trusted developer-input portfolio boundary.

[OD-022](DELIVERY_READINESS_AND_OPEN_DECISIONS.md#od-022--portfolio-mvp-yagni-simplification) keeps this workflow but narrows its implementation obligations to an in-process exact vector search, one `run.json` aggregate, at most one current review decision for a proposal and exactly one only after review completes, and an exact-locator public-page comparison. It removes a persistent vector service, independently versioned child records, audit-style review history, and generalized correlation machinery from the MVP. [ADR-0022](../architecture/decisions/ADR-0022-closed-versioned-guidance-corpus.md) records the already accepted closed source and deterministic passage boundary as architecture authority.

[OD-024](DELIVERY_READINESS_AND_OPEN_DECISIONS.md#od-024--minimum-complete-mvp-behavior-contracts) accepts the remaining workflow Must requirements only at their smallest useful scope: comparison-required scanner evidence, a proposal-or-abstention output contract, minimum actual-call provenance, an exact manifest-declared controlled comparison, and a canonical evidence-oriented interface. Exact TypeScript fields and other implementation literals remain open for the applicable implementation slice.

OD-020 supersedes OD-019's synthetic-only, one-profile/one-rule/one-target runtime boundary and the applicable cardinality portion of OD-018. OD-021 supersedes OD-020 only where it required a separate authorization attestation, hostile-target isolation, public-address enforcement, connection-level egress gating, and exhaustive pre-development resource qualification. OD-003 and OD-019 remain preserved as controlled evaluation-fixture history. Rows marked **Superseded** below retain their stable IDs and identify their replacements rather than silently changing accepted history.

The public-page scope does not authorize implementation by itself. The developer owns target authorization, and hostile or private pages are unsupported. The proportional browser, evidence, provider, and data-flow boundaries in ADR-0018 and the owning requirements apply; the production hardening formerly required by ADR-0017 no longer blocks this portfolio slice.

### Runtime handoff boundaries

| From | To | Minimum handoff |
| --- | --- | --- |
| Target intake | Scan | One basically parsed developer-supplied public HTTPS target, explicit Analyze action, trusted-input limitation, single-page scope, exact three-rule scan profile, and immutable global generation-mode context. |
| Scan | Evidence capture | One runtime-validated transient native axe result plus page/scan/coverage provenance. The scan step creates no durable normalized finding by itself. |
| Evidence capture | Results interface | One complete Finding collection containing every retained violation node, plus distinct minimized native `incomplete` observations and exact rule-coverage status in the same run aggregate. |
| Selected Finding | Retrieval | One selected Finding, its minimized sanitized source evidence, exact rule metadata, and approved rule-to-guidance mapping. No sibling finding content or comparison locator enters the query. |
| Retrieval | Generation | One nested per-finding retrieval result containing the privacy-safe query representation, corpus snapshot, top three passages with scores and citation metadata, and support state. |
| Evidence-sufficiency gate | Abstention | Incomplete required Finding evidence, or a completed retrieval with `incomplete`, `missing`, or `conflicting` support, produces one terminal application-authored abstention that references available evidence and retrieval, clearly explains the blocking state and missing or conflicting information, confirms that no model was called, and provides manual-investigation guidance. A retrieval execution or passage-integrity error fails the FindingWorkflow with no support state. An abstention has no ProviderInvocation or proposal-review decision. |
| Generation | Proposal review | One structurally valid, clearly AI-generated finding-specific proposal with inspectable references. Invocation provenance exists because a call was attempted, and only this proposal branch may enter approve/edit/reject review. |
| Selected baseline Finding | Rescan/comparison | One retained baseline Finding and its immutable scan evidence. Retrieval, generation or abstention, ProviderInvocation, proposal, and review are not prerequisites. |
| Later scan | Comparison | One complete baseline/later page pair; the retained locator or its unavailability reason; the exact rule-and-locator evidence for any attempted public-page match; any required later positive observation; and rule-specific measurements. Proposal, review, and manual-judgment data may be shown only as context and neither gate nor change comparison. |

### Eligibility and independence gates

| Gate | Minimum rule |
| --- | --- |
| Scan completion | All three accepted rules must execute under the recorded profile and every returned violation node must cross the validated minimized-evidence boundary. Missing, invalid, incomplete, or silently truncated coverage cannot complete. A complete scan may truthfully contain zero Findings. |
| Scanner observation classification | One axe violation node becomes one Finding. A native `incomplete` node becomes a ScannerReviewObservation and is never proposal-eligible. Native `passes` or `inapplicable` results are not general finding-list entries; retain only a narrow positive observation required for an identified comparison target. |
| Finding selection | Every Finding remains visible, but only one FindingWorkflow may be selected and active at a time. No automatic fan-out, combined query, queue, or bulk action follows from the collection. |
| Retrieval to generation | Only complete required evidence plus a completed `supported` retrieval may invoke the run's selected provider. Incomplete required Finding evidence, or a completed retrieval with `incomplete`, `missing`, or `conflicting` support, creates a terminal finding-specific abstention with a clear application-authored explanation and manual-investigation guidance, without a call or proposal-review decision. A retrieval execution or passage-integrity error is a workflow failure and has no support state. |
| Generation to proposal review | Only a validated `proposal` branch with resolvable evidence/passage references and no prohibited claim enters pending review. An abstention is not approvable. |
| Proposal to accepted plan | The reviewer must confirm that each material claim in the resulting proposal has the required support from cited guidance, recorded scanner evidence, or both. The reviewer must also record the profile's blocking pre-acceptance manual judgment. An unsupported material claim requires a resolving edit or rejection. Approval affects only that proposal/Finding; the post-change verification reminder remains non-blocking guidance. This gate creates no per-claim record. |
| Scan pair to comparison | Both scans must be complete and use the same page and scan profile. Public-page correlation requires the same rule and one valid retained locator that matches uniquely. A missing, invalid, or withheld baseline locator makes target correlation unavailable and a requested comparison `inconclusive`; a missing, changed, duplicate, or ambiguous later match is likewise `inconclusive`. Absence from a later violation list alone is never `resolved`. |

### Supported rule profiles and controlled evaluation inputs

Every runtime scan executes all three profiles and may retain multiple Findings per row. The controlled states are deterministic evaluation inputs only.

| Rule profile | Runtime minimized evidence | Minimum curated guidance | Model and human boundary | Conservative comparison |
| --- | --- | --- | --- | --- |
| `informative-image-alt` — axe `image-alt`, WCAG 2.2 SC 1.1.1 | Per violation node: native result/check identity, minimized target evidence, element kind, bounded sanitized `img`/`alt` state, exact scanner/evidence provenance, and either the one bounded locator accepted by `REQ-EVID-010` or its concise unavailability reason. | Normative SC 1.1.1, Understanding SC 1.1.1, H37, and H67. | The model may explain the observed missing alternative and conditional treatments. A person determines actual purpose/context and appropriate final treatment. | Exact matched failure-to-failure is `persistent`; `resolved` needs a unique later same-target non-failing observation plus complete coverage. No `improved`. |
| `form-input-label` — axe `label`, WCAG 2.2 SC 4.1.2 | Per violation node: native result/check identity, minimized target evidence, input type, bounded label/name-source association facts, no input value, and either the one bounded locator accepted by `REQ-EVID-010` or its concise unavailability reason. | Normative SC 4.1.2, Understanding SC 4.1.2, and H44. | The model may explain the missing programmatic name and applicable association patterns. A person judges clarity, accuracy, association, and additional instructions. | The same binary boundary applies; a changed but still-failing target is `persistent`, not `improved`. |
| `text-contrast` — axe `color-contrast`, WCAG 2.2 SC 1.4.3 | Per violation node: native result/check identity, minimized target evidence, axe-emitted foreground/background, measured and expected ratios, font size/weight, measurement provenance, and either the one bounded locator accepted by `REQ-EVID-010` or its concise unavailability reason. Any native `incomplete` result and reason remain in a separate ScannerReviewObservation. | Normative SC 1.4.3, Understanding SC 1.4.3, and G18. | The model may explain the retained shortfall and conditional color changes. A person verifies text classification, exceptions, background/design meaning, and omitted states. | Native failing-to-non-failing may be `resolved`. Two exact matched failures use the retained contrast margin: higher `improved`, equal `persistent`, lower `regressed`; missing/mismatched evidence is `inconclusive`. |

The narrow rule mappings are grounded in axe-core's versioned [`image-alt`](https://github.com/dequelabs/axe-core/blob/v4.13.0/lib/rules/image-alt.json), [`label`](https://github.com/dequelabs/axe-core/blob/v4.13.0/lib/rules/label.json), and [`color-contrast`](https://github.com/dequelabs/axe-core/blob/v4.13.0/lib/rules/color-contrast.json) metadata and WCAG 2.2 [SC 1.1.1](https://www.w3.org/TR/WCAG22/#non-text-content), [SC 4.1.2](https://www.w3.org/TR/WCAG22/#name-role-value), and [SC 1.4.3](https://www.w3.org/TR/WCAG22/#contrast-minimum). One automated node never proves complete success-criterion or page-level non-conformance.

## Corpus and retrieval

**Source-pack decision:** Accepted through OD-004. Runtime public-page scope does not expand the curated corpus or authorize web search, crawling, or recursive source loading.

The shared first-slice corpus remains the closed eight-artifact W3C guidance pack:

1. Normative [WCAG 2.2 Recommendation dated 12 December 2024](https://www.w3.org/TR/2024/REC-WCAG22-20241212/) sections for SC 1.1.1, SC 4.1.2, and SC 1.4.3 plus needed definitions.
2. [Understanding SC 1.1.1](https://www.w3.org/WAI/WCAG22/Understanding/non-text-content.html).
3. [Technique H37](https://www.w3.org/WAI/WCAG22/Techniques/html/H37).
4. [Technique H67](https://www.w3.org/WAI/WCAG22/Techniques/html/H67).
5. [Understanding SC 4.1.2](https://www.w3.org/WAI/WCAG22/Understanding/name-role-value.html).
6. [Technique H44](https://www.w3.org/WAI/WCAG22/Techniques/html/H44).
7. [Understanding SC 1.4.3](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html).
8. [Technique G18](https://www.w3.org/WAI/WCAG22/Techniques/general/G18).

WCAG success criteria are normative. Understanding documents and Techniques are informative and must not be presented as independent conformance requirements. The selected material must follow WAI's [Using WAI Material](https://www.w3.org/WAI/about/using-wai-material/) guidance and the applicable [W3C Document License](https://www.w3.org/copyright/document-license-2023/). Runtime page scanning does not crawl or add target-page content to the corpus.

The nested result records the corpus version, embedding model identity, privacy-safe query fields, filter, ordered passage IDs and scores, and support outcome. A persistent vector service, index lifecycle, hybrid search, and reranker are outside the MVP. | Must | Accepted through OD-022 and ADR-0019 | Lazy-build, query-embedding, ranking, provenance, and no-service inspection |

The accepted support-state policy is deterministic and applies after the top-three passage IDs resolve against the active corpus. Finding-evidence completeness is a separate pre-generation gate:

| Support state | Deterministic meaning |
| --- | --- |
| `conflicting` | The returned applicable set contains a curator-declared unresolved material conflict after normative guidance takes precedence over informative guidance. |
| `missing` | Retrieval completes but zero applicable passages resolve for the mapped rule and success criterion. |
| `incomplete` | At least one applicable passage resolves, but one or more profile-required guidance roles are absent from the returned set. |
| `supported` | Every profile-required guidance role resolves within the returned top three and no unresolved material conflict applies. |

Evaluation order is execution/integrity error with no support state, then `conflicting`, `missing`, `incomplete`, and finally `supported`. Similarity score alone never determines support. A retrieval execution or passage-integrity error fails the selected FindingWorkflow, has no support state, leaves the Finding/evidence visible, and must not be reported as missing guidance.

The outcome names describe scanner evidence only. Controlled fixtures use their stable project-owned target keys; public-page use is limited to the exact-match behavior accepted in `REQ-COMP-007` and `REQ-COMP-008`:

`REQ-COMP-006` governs persisted public runtime comparison data and therefore always references a baseline Finding. The fixed evaluation may exercise the controlled positive-to-violation binary rule and the [still-failing contrast ordering rule](evaluation-and-release/EVALUATION_AND_ACCEPTANCE.md#comparison-only-contrast-policy-vector) with small comparison-policy input vectors. These contain only the fields consumed by deterministic classification; they are not retained evidence records under `REQ-EVID-002`, canonical PageAnalysisRun comparisons, new domain identities, or evidence of browser-scanner fidelity.

| Outcome | Meaning |
| --- | --- |
| New (Deferred) | A possible future classification for a later-only Finding. The MVP shows it as unmatched later evidence and does not infer regression or causality. |
| Resolved | The baseline Finding is no longer reported, later coverage is complete, and a unique same-target native non-failing observation exists. This does not prove the underlying issue is fully fixed. |
| Improved | A correlated `color-contrast` Finding remains natively failing but its retained contrast margin is strictly higher under an identical measurement profile. It remains unresolved. |
| Persistent | A correlated Finding remains reportable in both scans; binary evidence changes stay visible, while contrast persistence requires equal retained margins. |
| Regressed | For public runtime comparison, exact matched baseline and later `color-contrast` violations have a lower later contrast margin under an identical measurement profile. For controlled-fixture evaluation only, a retained same-target non-failing baseline may become a later violation. Binary public comparisons cannot produce this outcome because they begin with a baseline Finding. |
| Inconclusive | The pair is generally comparable but target correlation or required evidence is missing, duplicate, changed, ambiguous, or conflicting. |
| Not comparable | Two complete scans differ in a material page identity, rule profile, environment, evidence policy, measurement profile, or coverage prerequisite. An invalid source scan fails rather than receiving this outcome. |

The trusted-target boundary is governed separately and supplies no deterministic comparison input.
