# Candidate architecture

## Authority and status

This document is Proposed architecture research referenced by, but not part of, the authoritative requirements baseline indexed by [Project requirements](../PROJECT_REQUIREMENTS.md). It is not an accepted ADR, implementation authority, dependency selection, or release qualification. Accepted architecture decisions remain under [Architecture Decision Records](decisions/README.md).

## Proposed architecture and technology constraints

**Status:** The provider-neutral generation boundary, Groq MVP adapter and dual-mode policy, localhost-browser execution topology, filesystem parent/child run boundary, and trusted operator URL boundary are Accepted in ADR-0001, ADRs 0014 through 0016, and ADR-0018. ADR-0002 and ADR-0017 are preserved as superseded MVP history; installer, packaging, and production hostile-URL containment are deferred. ADR-0003, ADRs 0005 through 0009, ADRs 0011 through 0013, and ADR-0014's exact Groq model accept named models or technologies only as bounded evaluation configurations; ADR-0010 records the reranker deferral. None of those evaluation choices is implemented, bundled, generally supported, or release-qualified.

The preferred first-slice architecture is one local application service plus an unprivileged React interface opened in Chrome or Edge at localhost. Ordinary TypeScript modules own the application workflow, Playwright opens the trusted operator-supplied page in a fresh non-persistent managed Chromium context, LangChain composes bounded retrieval and—only after the application-owned evidence-sufficiency gate—one structured generation call for one selected finding, and canonical JSON records remain on the local filesystem. The application adds no egress proxy, application worker, IPC protocol, queue, agent graph, or workflow engine. The selected Chroma and Ollama candidates may remain separate local tool services because those are evaluated adapter boundaries, not application microservices. One global `Local` or `Groq` mode belongs to a `PageAnalysisRun`; neither is a fallback, and mode selection does not invoke a provider. A distributed or hosted multi-user architecture is deferred.

The accepted operating path begins with one trusted operator-entered public HTTPS URL per `PageAnalysisRun`. Authorization and trust are operator responsibilities disclosed through a visible supported-use limitation, not a separate application attestation gate. One atomic scan in a fresh non-persistent context executes exactly `image-alt`, `label`, and `color-contrast` against one top-level main-document state and lists every returned violation node as a `Finding` plus every native axe `incomplete` node as a separate `ScannerReviewObservation`. Full scan coverage is explicit, and zero Findings is valid only for a completed, valid rule and collection result. The user then selects one Finding at a time for a sequential `FindingWorkflow`; scanner-review observations never enter that path, and other Findings remain deterministic records until selected. The path includes no authenticated target, existing-browser attachment, intentional page interaction or downloads, crawling, crawler implementation, automatic multi-finding orchestration, agent, queue, or workflow engine.

Exactly three independent, project-owned controlled profiles remain the fixed evaluation baseline: `informative-image-alt` (`image-alt`/SC 1.1.1), `form-input-label` (`label`/SC 4.1.2), and `text-contrast` (`color-contrast`/SC 1.4.3), each with failing and corrected revisions. They supply reproducible rule, evidence, provider, abstention, review, and comparison cases through the controlled evaluation path; they do not enter the user-submitted runtime URL path. Production URL containment and quantitative public-page resource qualification are deferred by [ADR-0018](decisions/ADR-0018-trusted-operator-url-boundary.md), not pre-development blockers.

## First-slice candidate patterns

**Status: Proposed candidate.** This section records coherent implementation shapes to evaluate after development is authorized. It does not accept the shape, select the named supporting tools, or authorize copying code. The detailed external implementation references and provenance constraints are recorded in [Voxleaf implementation pattern assessment](candidates/VOXLEAF_IMPLEMENTATION_PATTERN_ASSESSMENT.md).

| Candidate pattern | Proposed implementation shape | Adoption gate and explicit non-goals |
| --- | --- | --- |
| Authorized deterministic scan slice | One service-owned module accepts one trusted operator-entered public HTTPS URL, shows the supported-use limitation without a separate attestation gate, launches a fresh non-persistent managed Chromium context without imported state, applies a finite navigation timeout, and runs exactly `image-alt`, `label`, and `color-contrast` atomically without scanning subframes. It validates all-rule coverage and returns every violation node, separate native `incomplete` observations, and an explicit full-result disposition before cleanup. | ADR-0018 accepts this bounded portfolio behavior while deferring production hostile-URL containment. Step 1 owns execution and transient native results; [Step 2](candidates/ACCESSIBILITY_FINDING_EVIDENCE_CAPTURE_ASSESSMENT.md) owns allowlisting, sanitization, rule-specific normalization, digests, durable Findings, and separate `ScannerReviewObservation` records. No authentication, interaction, downloads, crawling, or crawler implementation is included. |
| Minimal record boundary | Small application-owned TypeScript record definitions describe URL syntax/admission, the parent `PageAnalysisRun`, finding-workflow children, optional provider invocation, and exact handoffs among the workflow steps, with runtime validation at URL syntax, axe, Groq, the local runtime, and persisted JSON. | Accepted in principle by the applicable requirements and scoped by ADR-0011, ADR-0016, and ADR-0018. The first slice does not require JSON Schema as a canonical contract, code generation, a schema framework, migrations, multiple schema dialects, or a compatibility framework. |
| Manual micro-corpus preparation | A bounded frozen W3C source pack covering the three selected success criteria and minimum scenario-specific techniques is divided manually into deterministic heading-aware passages with stable source locators and application-owned identities, then embedded once. | OD-004 accepts the bounded pack subject to the W3C/WAI use conditions documented in the [curated guidance corpus assessment](candidates/guidance-retrieval/CURATED_GUIDANCE_CORPUS_ASSESSMENT.md#proposed-deterministic-source-preparation). Public availability does not remove attribution, copyright, status, or update obligations. Axe metadata maps the finding to the corpus but is not embedded guidance. |
| Thin two-step RAG | Application code builds the deterministic privacy-safe query for one user-selected finding, LangChain composes vector retrieval, application policy admits only complete evidence with `supported` retrieval, and an eligible path makes at most one structured model call; all other support states abstain before invocation. Deterministic validation checks references and prohibited claims. | ADR-0013 accepts this only as an evaluation baseline. No page-wide prompt, provider batch, agent, reranker, query rewriting, critique model, or semantic judge is included. |
| Sequential operation ownership | One parent `PageAnalysisRun` owns the immutable atomic scan and finding index. The user starts at most one current `FindingWorkflow` child at a time for one selected finding. Retrying a failed scan or child creates a new linked `PageAnalysisRun`; no earlier parent or child is overwritten or resumed. | No automatic all-findings orchestration, queue, replacement controller, cancellation, checkpoint engine, application worker, resume, or partial-success claim is required. The global `Local` or `Groq` context is immutable within the parent and never causes an implicit invocation. |
| Portfolio evaluation | One frozen happy-path generation case for each of the three synthetic profiles runs locally, and the same three cases run through Groq. Shared deterministic abstention and comparison checks are not duplicated per provider. Scan evaluation covers trusted-URL syntax, visible supported-use limitations, fresh-context use, timeout/failure visibility, cleanup, all-node handling, incomplete observations, and valid-zero semantics. | The compact synthetic manifest remains non-promotable and supports no statistical, leaderboard, provider-comparison, broad coverage, compliance, security, support, or release claim. Hostile-network and adversarial URL qualification are outside the MVP. |
| Bounded React presentation | Application code supplies only the bounded, application-owned evidence, guidance, generation, review, and comparison text needed by the current view; React renders the four information layers and one proposal decision with native semantics. | ADR-0012 accepts only React's evaluation baseline. No formal closed-view-model or exhaustive renderer-qualification program, router, state library, component kit, desktop container, or workflow library is part of the MVP. |
| Minimal local persistence | Persist one minimized parent page-analysis graph containing every retained Finding and its evidence reference, plus one independently versioned child state only for each FindingWorkflow the user actually starts. Create provider-invocation data only when a call is attempted. | ADR-0016 accepts one local parent directory with canonical JSON, optional selected-finding child records, and an optional Markdown report. Browser Web Storage is not the durable authority; no database, backup, sync, or migration framework is included. |

## Deferred candidates requiring evidence

The following ideas remain useful research candidates identified during architecture planning, including applicable patterns from the Voxleaf assessment. YAGNI excludes them from the first slice, and they may be evaluated only after the named trigger exists.

| Candidate | Trigger before evaluation |
| --- | --- |
| Generated serialized-contract pipeline | More than one producer, persisted schema version, or import/export boundary creates demonstrated drift risk. |
| Identity-first queue, cancellation, and checkpoint controller | Concurrent, replaceable, resumable, or long-running application work is accepted into scope. |
| Hostile-URL containment and supervised browser isolation | A later product accepts untrusted targets, is distributed beyond the developer portfolio context, or claims safe general-Internet scanning. A new threat model and ADR must then select connection mediation, address policy, resource bounds, browser isolation, cleanup qualification, and any required helper-process ownership. |
| Managed optional-artifact acquisition | Distribution and application-owned runtime/model installation enter scope; do not duplicate a selected runtime's safe lifecycle. |
| Full backup, migration, and cascading deletion | Private page projects, multiple stored versions, or distributable retention controls enter scope. |
| Exact release inventory, signing, repair, and uninstall evidence | A distributable Windows release is authorized. |
| Formal evaluation authority and support matrix | The project intends to promote results, compare providers publicly, or make support claims. |
| Compatibility/readiness report | The project supports hardware beyond the documented reference PC. |
| [One constrained configurable remote-generation profile](../requirements/generation-provider-and-model-lifecycle/GENERATION_PROVIDER_EXECUTION.md) | The completed MVP demonstrates its fixed local/Groq paths and a later product need justifies replacing the Groq remote slot with one approved HTTPS origin, model, authentication method, and protocol subset. Evaluation requires accepted provider-selection, threat-model, and data-flow decisions first. This is not a third MVP mode, a provider registry, or general OpenAI-compatible support. |

ADR-0017's production-oriented security design remains useful decision history, but [ADR-0018](decisions/ADR-0018-trusted-operator-url-boundary.md) explicitly defers it for the portfolio MVP. Application-owned egress mediation, redirect and subresource revalidation, public-address classification, DNS pinning, network and resource ceilings, hostile-page isolation, and adversarial URL qualification require a later demonstrated product need, threat model, and ADR. They are not implied by the fresh-context hygiene used for the trusted operator target and do not block first-slice development.
