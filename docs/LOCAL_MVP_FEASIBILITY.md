# Local MVP feasibility

## Status

The named technologies in this assessment are not implemented behavior. ADR-0003, ADRs 0005 through 0009, ADRs 0011 through 0013, and ADR-0014's exact Groq model accept named models or technologies only as bounded evaluation configurations; ADR-0010 records the explicit reranker deferral. ADR-0014 separately accepts Groq and no fallback as binding MVP architecture. ADR-0015 and ADR-0016 accept the MVP execution topology and filesystem record boundary without selecting their remaining implementation details. [ADR-0017](architecture/decisions/ADR-0017-authorized-public-page-scan-boundary.md) accepts the mandatory trust boundary for one public HTTPS target; it does not select exact numeric scan limits or promote Playwright or axe-core beyond their evaluation status. Acceptance for evaluation does not qualify a technology as bundled, generally supported, or a release dependency.

The separate [authorized deterministic web scan assessment family](architecture/candidates/authorized-scan/README.md) and [Voxleaf implementation pattern assessment](architecture/candidates/VOXLEAF_IMPLEMENTATION_PATTERN_ASSESSMENT.md) contain **Proposed research inputs only** beyond the configurations and boundaries already accepted by ADR. They do not authorize implementation, bundling, general support, or release and do not change any ADR's scope. The compact decisions recorded on 2026-08-25 resolve the MVP parts of OD-003 through OD-018 while explicitly deferring production-scale and release concerns. [OD-020](requirements/DELIVERY_READINESS_AND_OPEN_DECISIONS.md#od-020--authorized-public-page-analysis-scope) supersedes OD-019 only as the runtime-input and scan-cardinality authority; OD-019's three synthetic profiles remain the fixed evaluation baseline.

Assessment date: 2026-08-23. Scope amendments: 2026-08-24 and 2026-08-25. This is a preliminary assessment based on published model artifacts and a hardware snapshot; representative evaluation is required once development begins.

## Local feasibility hypothesis

The current computer is the accepted reference machine for testing whether the complete A11y Evidence Lab MVP can run locally. No representative end-to-end evaluation has been completed, so runtime fit, observed duration, model quality, context capacity, and sustained stability remain unverified.

The accepted portfolio scope now starts one analysis from one user-entered, explicitly authorized public HTTPS page. One atomic, provider-independent scan runs exactly axe `image-alt`, `label`, and `color-contrast` and lists every violation node within the accepted resource envelope; native incomplete observations remain distinct. Downstream retrieval, generation or abstention, review, and comparison remain sequential for one selected finding at a time. Authentication, non-public destinations, crawling, target discovery, broader rule coverage, and bulk generation remain outside the MVP. The project-owned `informative-image-alt`, `form-input-label`, and `text-contrast` profiles remain fixed synthetic evaluation cases and do not become proof that live-target behavior is safe, deterministic, or broadly supported.

Local feasibility is an MVP constraint for the complete local-generation path, even though an analysis may instead select the Groq adapter accepted by ADR-0014. A public-page scan necessarily makes only the target-network requests permitted by ADR-0017, so local generation means no hosted inference rather than an offline analysis. Passing the Groq-backed evaluation cannot substitute for completing the local workflow on the reference machine.

Hardware and available-storage snapshot used for this assessment:

- **32 GB of RAM**
- **Intel Core Ultra 7 255HX** with 20 cores
- **NVIDIA RTX 5060 Laptop GPU with 8 GB of VRAM**
- Approximately **513 GB of free disk space**

Ollama documents native [Windows support](https://docs.ollama.com/windows) and [NVIDIA GPU acceleration](https://docs.ollama.com/gpu), so the RTX GPU is a candidate accelerator for embeddings and text generation. Current driver compatibility and actual GPU offload must be verified on the reference machine before development relies on acceleration.

## Application-stack implications

[ADR-0011](architecture/decisions/ADR-0011-typescript-as-initial-application-language.md) applies TypeScript to the application-owned UI, local service, records, adapters, retrieval integration, and browser-analysis module for the first evaluation. Compile-time types do not validate runtime data, so public-URL and network-policy decisions, navigation results, native axe collections, Groq responses, selected local-runtime responses, and persisted JSON must be validated before entering domain logic. The MVP does not need a schema framework, code generation, migrations, multiple schema dialects, or a compatibility framework.

[ADR-0012](architecture/decisions/ADR-0012-react-as-initial-user-interface-library.md) limits React to the client-rendered interface. [ADR-0015](architecture/decisions/ADR-0015-localhost-browser-mvp-execution.md) places durable records, credentials, filesystem/process access, provider calls, model/vector services, and Playwright in the developer-started local service; Chrome or Edge displays only the localhost UI. The choices do not imply Vite, Next.js, Electron, Tauri, WebView2, Node.js, an installer, or another runtime or container.

The [scan technology selection assessment](architecture/candidates/authorized-scan/TECHNOLOGY_SELECTION.md) proposes Node.js 24 LTS only as the first host to evaluate for the Playwright and axe-core modules. OD-020's one atomic three-rule scan remains ordinary bounded application behavior; it does not add an application worker, IPC protocol, queue, supervisor, agent, or workflow engine. ADR-0017's trust boundary must be demonstrated before this topology is considered adequate for live public content. TypeScript does not imply that the isolation or resource policy has been implemented.

The TypeScript choice makes Chroma's documented client/server path relevant but does not accept it for release. For the MVP evaluation, Chroma may remain a separately evaluated loopback tool boundary and stores only a rebuildable corpus index, not canonical run records. Its practical lifecycle and isolation still require evaluation; broader service ownership, migration, packaging, and support qualification are deferred.

The `qwen3.5:4b` and `qwen3.5:9b` tags are convenient setup labels, but floating aliases and published metadata can change. Acquisition and evaluation records must capture the Ollama version, exact full model digest, quantization, configured context, license, generation parameters, and integrity result. The displayed digest prefixes above are research observations, not sufficient reproducibility identifiers.

## Local-model eligibility rule

[ADR-0004](architecture/decisions/ADR-0004-reference-pc-capacity-gate-for-local-models.md) makes the existing PC a hard boundary. Models whose published artifact, estimated runtime/context working set, storage, or runtime requirements clearly exceed that boundary are excluded before download and do not appear in the active candidate list. A borderline configuration receives only a bounded capacity preflight. It becomes an evaluation candidate only after completing that preflight with the representative browser, embedding, retrieval, and application services active, without out-of-memory or storage failure, and without making the interface unusable. Record observed duration, paging/fallback, memory, responsiveness, and thermal limitations as context; the MVP sets no formal percentile, latency, or thermal budget and makes no public performance claim.

The 4B configuration is only the first capacity screen because it leaves more nominal headroom for the embedding model, browser, local services, and context cache. It is not assumed to have adequate remediation quality or even final runtime fit. The 9B configuration is preserved only as historical feasibility context and is not screened in the fixed MVP. If the 4B candidate fails, select one smaller replacement that can pass on the same PC rather than adding a comparison candidate.

## Provider and local-acquisition implications

[ADR-0001](architecture/decisions/ADR-0001-interchangeable-generation-providers.md) requires local and external-API generation to use the same application-owned contract, validation, provenance, and evaluation rules. [ADR-0014](architecture/decisions/ADR-0014-groq-as-mvp-external-generation-provider.md) selects Groq as the only external MVP adapter and `openai/gpt-oss-20b` with strict Structured Outputs as its exact evaluation model. Groq is the provider even though its endpoint is mostly OpenAI compatible and the model ID uses an `openai/` namespace. There is no automatic fallback, second hosted provider, provider comparison, or release-support claim.

[ADR-0005](architecture/decisions/ADR-0005-ollama-as-initial-local-model-runtime.md) accepts Ollama only as the initial local runtime to evaluate, while [ADR-0003](architecture/decisions/ADR-0003-initial-local-generation-evaluation-preset.md) accepts `qwen3.5:4b` only as the first capacity-screen model configuration. ADR-0004 excludes any configuration from the compact local evaluation if it fails that screen. The user explicitly downloads the selected local model through the selected runtime, outside the repository and any installer, after the source, identity, transfer/storage information, destination, and network requirement are disclosed. Ollama documents native [Windows operation](https://docs.ollama.com/windows), separate model storage, and a [model-pull API](https://docs.ollama.com/api/pull).

[ADR-0002](architecture/decisions/ADR-0002-windows-installation-and-model-acquisition.md) is superseded for the MVP by [ADR-0015](architecture/decisions/ADR-0015-localhost-browser-mvp-execution.md). The developer starts the local service and opens the localhost UI in Chrome or Edge; there is no installer-managed first-run or packaging workflow. The MVP still requires minimal local setup: disclose and obtain explicit consent for a runtime-managed local model download, or configure the Groq credential in the local service. Before analysis the user chooses one global Local or Groq mode; the scan does not invoke it, and every later eligible generation call uses that same mode. Ollama's installed Windows application and update behavior still require practical local-generation egress evaluation. A Groq call sends only the selected finding's permitted minimized evidence and required guidance after the accepted disclosure; it never sends the raw page, target URL, unrelated findings, or credentials.

## Initial evaluation recommendation

Treat completion without additional hardware as a portfolio constraint, not a proven feasibility or performance conclusion. Start by evaluating the embedding candidate and running the bounded practical-capacity preflight for `qwen3.5:4b`. Only after it passes may the local mode run one frozen happy-path generation case for each of the three controlled scenarios. Run the same three happy cases through the fixed Groq configuration to demonstrate the second adapter, without treating the six runs as a provider comparison. Run shared deterministic abstention and comparison checks once rather than duplicating them per provider. Keep those synthetic cases as the reproducible generation baseline, and separately validate public-target policy enforcement, all-findings collection, native-incomplete separation, valid-zero coverage, and overflow failure without adding provider calls.

This compact manifest is fixed before model results are observed and is non-promotable: it supports no statistics, leaderboard, broad accessibility-coverage, live-page safety, compliance, support, or release claim. A second local comparison is excluded; if the first candidate fails, select one smaller replacement and rerun the same screen. `qwen3.5:9b` is Deferred for the MVP. Record task limitations, context fit, observed duration, peak RAM and VRAM, disk use, UI responsiveness, and material sustained-run behavior. Exact numeric live-scan limits remain open, but exceeding any eventual accepted limit must be fail-visible and must never produce silent truncation. The MVP has no formal latency percentile, thermal budget, public performance target, packaging measurement, or broad support matrix, and Groq results never relax the local capacity gate.
