# Local MVP feasibility

## Status

The named technologies in this assessment are not implemented behavior. ADR-0003, ADRs 0005 through 0009, and ADRs 0011 through 0013 accept them only as initial evaluation baselines; ADR-0010 records the explicit reranker deferral. Acceptance for evaluation means that these are the first configurations to measure after development is authorized; it does not qualify them as bundled, supported, or release dependencies. Exact release technologies remain subject to the documented gates and later decisions.

The separate [authorized deterministic web scan assessment family](architecture/candidates/authorized-scan/README.md) and [Voxleaf implementation pattern assessment](architecture/candidates/VOXLEAF_IMPLEMENTATION_PATTERN_ASSESSMENT.md) contain **Proposed research inputs only** beyond the evaluation baselines already accepted by ADR. They do not authorize implementation, bundling, support, release, or live-target scanning and do not change any ADR's scope. The applicable unresolved choices are tracked in [Delivery readiness and open decisions](requirements/DELIVERY_READINESS_AND_OPEN_DECISIONS.md#decisions-required-before-development), including the stage-relevant parts of OD-003, OD-006, OD-009 through OD-012, and OD-014 through OD-018. OD-002 and OD-005 are resolved for the first portfolio slice.

Assessment date: 2026-08-23. This is a preliminary assessment based on published model artifacts and a hardware snapshot; representative benchmarks are required once development begins.

## Local feasibility hypothesis

The current computer is the proposed reference machine for testing whether the complete A11y Evidence Lab MVP can run locally. No representative end-to-end benchmark has been completed, so runtime fit, latency, model quality, context capacity, and sustained stability remain unverified.

Local feasibility is a release constraint for the complete local-only path, even though the product will also support a separately selected external-API generation provider. Passing an API-backed evaluation cannot substitute for passing the local workflow on the reference machine.

Hardware and available-storage snapshot used for this assessment:

- **32 GB of RAM**
- **Intel Core Ultra 7 255HX** with 20 cores
- **NVIDIA RTX 5060 Laptop GPU with 8 GB of VRAM**
- Approximately **513 GB of free disk space**

Ollama documents native [Windows support](https://docs.ollama.com/windows) and [NVIDIA GPU acceleration](https://docs.ollama.com/gpu), so the RTX GPU is a candidate accelerator for embeddings and text generation. Current driver compatibility and actual GPU offload must be verified on the reference machine before development relies on acceleration.

## Application-stack implications

[ADR-0011](architecture/decisions/ADR-0011-typescript-as-initial-application-language.md) applies TypeScript to the application-owned UI, local service, contracts, adapters, retrieval integration, and browser-analysis module for the first evaluation. Compile-time types do not validate external runtime data, so scanner, provider, model, storage, import, and actual process-boundary values must still be validated before entering domain logic.

[ADR-0012](architecture/decisions/ADR-0012-react-as-initial-user-interface-library.md) limits React to the client-rendered interface. Durable evidence, workflow and review state, credentials, filesystem and process access, provider calls, model and vector services, and Playwright remain behind the authenticated local application API. The choice does not imply Vite, Next.js, Electron, Tauri, WebView2, Node.js, or another runtime or container.

The [scan technology selection assessment](architecture/candidates/authorized-scan/TECHNOLOGY_SELECTION.md) proposes Node.js 24 LTS only as the first host to evaluate for the Playwright and axe-core modules. The first controlled-fixture slice does not add an application worker, IPC protocol, queue, or supervisor. A later live-page threat model or measured reliability need may justify process isolation, but TypeScript does not imply it.

The TypeScript choice makes Chroma's documented client/server path relevant but does not accept it for release. OD-014 must decide whether the application owns a Chroma loopback service, uses an approved helper, selects a different compatible mode, or replaces Chroma after evaluation. That decision must include service authentication and isolation, lifecycle, recovery, migration, packaging, and concurrent resource measurements.

The `qwen3.5:4b` and `qwen3.5:9b` tags are convenient setup labels, but floating aliases and published metadata can change. Provisioning and benchmark records must capture the Ollama version, exact full model digest, quantization, configured context, license, generation parameters, and integrity result. The displayed digest prefixes above are research observations, not sufficient release integrity identifiers.

## Local-model eligibility rule

[ADR-0004](architecture/decisions/ADR-0004-reference-pc-capacity-gate-for-local-models.md) makes the existing PC a hard boundary. Models whose published artifact, estimated runtime/context working set, storage, or runtime requirements clearly exceed that boundary are excluded before download and do not appear in the active candidate list. A borderline configuration receives only a bounded capacity preflight. It becomes an evaluation candidate only after completing that preflight with the representative browser, embedding, retrieval, and application services active and without unacceptable memory, paging, responsiveness, latency, storage, or thermal behavior.

The 4B configuration is only the first capacity screen because it leaves more nominal headroom for the embedding model, browser, local services, and context cache. It is not assumed to have adequate remediation quality or even final runtime fit. The 9B configuration is not a required comparison: it may be screened only if the metadata prefilter finds it plausible, and a failed preflight removes it from consideration in favor of another smaller configuration that can pass on the same PC.

## Provider and first-run implications

[ADR-0001](architecture/decisions/ADR-0001-interchangeable-generation-providers.md) requires local and external-API generation to use the same application-owned contract, validation, provenance, and evaluation rules. [ADR-0005](architecture/decisions/ADR-0005-ollama-as-initial-local-model-runtime.md) accepts Ollama only as the initial local runtime to evaluate, while [ADR-0003](architecture/decisions/ADR-0003-initial-local-generation-evaluation-preset.md) accepts `qwen3.5:4b` only as the first capacity-screen model configuration. ADR-0004 excludes any configuration from full evaluation if it fails that screen. The exact external API adapter and release local runtime remain open.

[ADR-0002](architecture/decisions/ADR-0002-windows-installation-and-model-acquisition.md) keeps large model artifacts outside the Windows installer. First-run setup detects a supported local runtime and installed models, then offers the selected model download only after disclosing its source, license, transfer size, estimated storage, destination, and network use. Ollama documents native Windows operation and separate model storage, and its API provides a model-pull operation with progress responses; see the official [Windows documentation](https://docs.ollama.com/windows) and [model-pull API](https://docs.ollama.com/api/pull).

Ollama's installed Windows application and its update behavior must be assessed against the zero-non-loopback-egress requirement. OD-014 must decide whether the product owns a pinned standalone runtime or integrates with an independently installed runtime whose updates and network behavior can be controlled and verified.

## Initial benchmark recommendation

Treat completion without additional hardware as a portfolio acceptance constraint, not a proven feasibility conclusion. Start by evaluating the embedding candidate and running the bounded capacity preflight for `qwen3.5:4b`. Only after it passes may it enter the fixed 5–10-case portfolio evaluation. A second configuration is unnecessary for that non-promotable demonstration unless the first fails; `qwen3.5:9b` remains optional and must be excluded if it does not fit. Measure the selected JavaScript runtime, React UI, Chroma topology, Playwright browser, Ollama, embedding, and generation workload together. Record task quality, context fit, latency, peak RAM and VRAM, disk use, UI responsiveness, and sustained-run stability. Broader recovery and packaging measurements are required only before a release configuration is selected, and external-adapter results never relax the local capacity gate.
