ADR-0007 is superseded Chroma history. ADR-0014 separately accepts Groq and no fallback as binding MVP architecture. ADR-0015, ADR-0020, and ADR-0021 own the current localhost execution, manual local-model setup, and single-file run boundaries. The separate [authorized deterministic web scan assessment family](architecture/candidates/authorized-scan/README.md) and [Voxleaf implementation pattern assessment](architecture/candidates/VOXLEAF_IMPLEMENTATION_PATTERN_ASSESSMENT.md) contain **Proposed research inputs only** beyond the configurations and boundaries already accepted by ADR. ## Local feasibility hypothesis

The current computer is the accepted reference machine for testing whether the complete A11y Evidence Lab MVP can run locally. No representative end-to-end evaluation has been completed, so runtime fit, observed duration, model quality, context capacity, and sustained stability remain unverified.

The accepted portfolio scope now starts one analysis from one user-entered public HTTPS page that the developer/operator treats as trusted and is responsible for authorizing. One atomic, provider-independent scan runs exactly axe `image-alt`, `label`, and `color-contrast` and lists every violation node reported by those rules; native incomplete observations remain distinct. Downstream work remains sequential for one selected finding at a time: incomplete required evidence or a completed `incomplete`, `missing`, or `conflicting` retrieval ends in a terminal application-authored abstention with an explanation and manual-investigation guidance, while a retrieval execution or integrity error remains a failure with no support state. Eligible generation may produce a proposal that alone enters human review. Comparison is a separate scan-evidence path that may start from any retained baseline Finding without prior retrieval, generation, abstention, or review. Authentication, crawling, target discovery, broader rule coverage, and bulk generation remain outside the MVP. The project-owned `informative-image-alt`, `form-input-label`, and `text-contrast` profiles remain fixed synthetic evaluation cases and do not become proof that live-target behavior is safe, deterministic, or broadly supported.

Local feasibility is an MVP constraint for the complete local-generation path, even though an analysis may instead select the Groq adapter accepted by ADR-0014. A public-page scan necessarily makes ordinary browser requests to the trusted target, so Local generation means that its prompts and responses use only the approved loopback runtime; it does not mean an offline analysis. Embedding computation and vectors also remain local in both generation modes, but an explicitly selected Groq action may still send the accepted minimized generation payload. The MVP does not mediate or qualify target requests or unrelated machine networking. Passing the Groq-backed evaluation cannot substitute for completing the local workflow on the reference machine.

Hardware and available-storage snapshot used for this assessment:

- **32 GB of RAM**
- **Intel Core Ultra 7 255HX** with 20 cores
- **NVIDIA RTX 5060 Laptop GPU with 8 GB of VRAM**
- Approximately **513 GB of free disk space**

Ollama documents native [Windows support](https://docs.ollama.com/windows) and [NVIDIA GPU acceleration](https://docs.ollama.com/gpu), so the RTX GPU is a candidate accelerator for embeddings and text generation. Current driver compatibility and actual GPU offload must be verified on the reference machine before development relies on acceleration.

## Application-stack implications

[ADR-0011](architecture/decisions/ADR-0011-typescript-as-initial-application-language.md) applies TypeScript to the application-owned UI, local service, records, adapters, retrieval integration, and browser-analysis module for the first evaluation. Compile-time types do not validate runtime data, so URL syntax, navigation results, native axe collections, Groq responses, selected local-runtime responses, and persisted JSON must be validated before entering domain logic. The MVP does not need a schema framework, code generation, migrations, multiple schema dialects, or a compatibility framework.

[ADR-0012](architecture/decisions/ADR-0012-react-as-initial-user-interface-library.md) limits React to the client-rendered interface. [ADR-0015](architecture/decisions/ADR-0015-localhost-browser-mvp-execution.md) places `run.json`, credentials, filesystem access, provider calls, in-process retrieval, and Playwright in the developer-started local service; Chrome or Edge displays only the localhost UI. The choices do not imply Vite, Next.js, Electron, Tauri, WebView2, Node.js, an installer, or another runtime or container.

The [scan technology selection assessment](architecture/candidates/authorized-scan/TECHNOLOGY_SELECTION.md) proposes Node.js 24 LTS only as the first host to evaluate for the Playwright and axe-core modules. OD-020's one atomic three-rule scan remains ordinary application behavior; it does not add an application worker, IPC protocol, queue, supervisor, agent, or workflow engine. ADR-0018 requires a fresh non-persistent context, no imported identity or authentication state, a simple finite navigation timeout, and cleanup. It deliberately does not require proof of public reachability or production security controls for malicious targets.

ADR-0019 removes a separate vector-service topology from the MVP. The small fixed corpus is embedded and searched in process through LangChain's in-memory exact-search integration; the canonical passages remain application-owned. Disposable vectors are built only when retrieval is first requested and therefore rebuilt on the first retrieval after a restart or relevant corpus/configuration change. Chroma remains superseded history and a later candidate only if corpus growth, mutability, persistence, or measured performance justifies it.

The `qwen3.5:4b` and `qwen3.5:9b` tags are convenient setup labels, but floating aliases and published metadata can change. The fixed evaluation notes should identify the observed Ollama version, model digest, and relevant generation configuration. The displayed digest prefixes above are research observations, not sufficient reproducibility identifiers.

## Local-model eligibility rule

[ADR-0004](architecture/decisions/ADR-0004-reference-pc-capacity-gate-for-local-models.md) makes the existing PC a hard boundary. Models whose published artifact, estimated runtime/context working set, storage, or runtime requirements clearly exceed that boundary are excluded before download. After the developer installs the one plausible fixed configuration, run one manual representative capacity smoke with the browser, embedding, retrieval, and application active. It enters evaluation only if that smoke completes without out-of-memory/storage failure or an unusable interface. Record readily observable duration, paging or offload to CPU/system memory, and responsiveness; no in-app hardware monitor, repeated benchmark, percentile, thermal budget, or public performance claim is required.

The 4B configuration is only the first capacity screen because it leaves more nominal headroom for the embedding model, browser, local services, and context cache. It is not assumed to have adequate remediation quality or even final runtime fit. The 9B configuration is preserved only as historical feasibility context and is not screened in the fixed MVP. If the 4B candidate fails, evaluation pauses until a new recorded model-selection decision identifies one smaller replacement and the exact-model requirement and evaluation configuration are updated; the replacement must pass on the same PC and does not become a comparison candidate or runtime fallback.

## Provider and local-setup implications

[ADR-0001](architecture/decisions/ADR-0001-interchangeable-generation-providers.md) requires local and external-API generation to use the same application-owned contract, validation, provenance, and evaluation rules. [ADR-0014](architecture/decisions/ADR-0014-groq-as-mvp-external-generation-provider.md) selects Groq as the only external MVP adapter and `openai/gpt-oss-20b` with strict Structured Outputs as its exact evaluation model. Groq is the provider even though its endpoint is mostly OpenAI compatible and the model ID uses an `openai/` namespace. There is no automatic fallback, second hosted provider, provider comparison, or release-support claim.

[ADR-0005](architecture/decisions/ADR-0005-ollama-as-initial-local-model-runtime.md) accepts Ollama only as the initial local runtime to evaluate, while ADR-0003 accepts `qwen3.5:4b` as the first local generation configuration. Under [ADR-0020](architecture/decisions/ADR-0020-manual-developer-managed-local-model-setup.md), the developer installs Ollama and runs `ollama pull embeddinggemma` outside A11y Evidence Lab before retrieval in either mode; Local generation additionally requires `ollama pull qwen3.5:4b`. The application provides no download button, progress state, model manager, or synthetic readiness probe. Ollama documents native [Windows operation](https://docs.ollama.com/windows) and the [`ollama pull` CLI](https://docs.ollama.com/cli).

[ADR-0002](architecture/decisions/ADR-0002-windows-installation-and-model-acquisition.md) is superseded for the MVP by ADR-0015. The developer starts the local service and installs Ollama plus `embeddinggemma` for retrieval in either generation mode. Local generation additionally needs `qwen3.5:4b`; Groq generation instead needs the Groq credential. At analysis start, one concise disclosure identifies the selected Local or Groq mode and the provider/model stays visible. Each eligible generation still requires an explicit action; the actual call and structured-output validation determine success, with no automatic fallback. A Groq call sends only the selected finding's permitted minimized evidence and required guidance.

[ADR-0023](architecture/decisions/ADR-0023-local-mode-data-boundary.md) makes the privacy claim role-specific: Local-generation prompts and responses use only Ollama loopback, and the embedding adapter uses no hosted embedding or vector service. Trusted-page loading, an explicitly selected minimized Groq generation call, and developer-managed model pulls are separate network operations. The MVP does not attempt to prove system-wide zero egress.

## Initial evaluation recommendation

Treat completion without additional hardware as a portfolio constraint, not a proven feasibility or performance conclusion. After manual model setup, run one representative capacity smoke for the local stack. Only after it passes may Local mode run one frozen happy-path generation case for each controlled scenario. Run the same three cases through Groq to demonstrate the second adapter, not to compare providers. Run shared deterministic abstention and comparison checks once. Separately validate trusted-HTTPS input, fresh-context behavior, no crawling or interaction, all-findings collection, native-incomplete separation, valid zero, visible scan failure, and cleanup without provider calls.

This compact manifest is fixed before model results are observed and is non-promotable: it supports no statistics, leaderboard, broad accessibility-coverage, live-page safety, compliance, support, or release claim. A second local comparison is excluded; if the first candidate fails, a new recorded model-selection decision must identify one smaller replacement before the exact configuration is updated and the same screen is rerun. `qwen3.5:9b` is Deferred for the MVP. Record task limitations, observed duration, model storage, obvious resource failure, and UI responsiveness. The MVP has one implementation-stage navigation-timeout value but no exhaustive numeric URL, redirect, request, response, memory, or node-count policy; those production controls are deferred. It also has no formal latency percentile, thermal budget, public performance target, packaging measurement, or broad support matrix, and Groq results never relax the local capacity gate.
